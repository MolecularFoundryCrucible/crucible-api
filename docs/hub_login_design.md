# Hub login design

Status: API implementation on `feat/hub-login-design`, integrated with the local Hub; not deployed to production.

Local integration is now working through Tailscale. The API public base URL is `https://leviathan.rooster-chimaera.ts.net/testapi` and the Hub callback is `https://leviathan.rooster-chimaera.ts.net/hub/auth/callback`. The ORCID redirect is the API base URL plus `/auth/hub/callback`. These override the earlier loopback reservation below. Production deployment remains gated by [authentication operations](hub_auth_operations.md).

This document records the API-side design for production Hub login. Before changing the Hub contract, coordinate the decision and update `crucible-hub/docs/authentication-transition.md`, its authentication decision, API integration documentation, pinned OpenAPI artifact, generated client, and tests. Do not change the Hub repository as part of this API branch without explicit authorization.

## Current boundary

The Hub is a backend-for-frontend: browser requests reach Hub server functions, which call the API. The browser must hold only an opaque Hub session cookie, never a Crucible API key or ORCID token. Each private Hub server function must authenticate its session; the API must still authorize each request. Hub must send `Crucible-Privilege-Mode: normal` for ordinary operations and request elevation only for explicit administrator operations.

Confirmed intended Hub callback: `https://crucible.lbl.gov/hub/auth/callback`. Its deployment through the reverse proxy still needs verification. API production and staging ORCID callbacks would remain under their respective external API paths. The checked-in `crucible-nginx/nginx.conf` currently proxies `/explore/` to Cloud Run but has no `/hub/` location. The Hub proxy must preserve the path prefix expected by its Node runtime, handle `/hub` consistently with `/hub/`, and pass a trusted external scheme and host without treating arbitrary client-supplied forwarded headers as authority. Register exact ORCID callback URLs only after the final external paths are verified at the edge. The Cloud Run service URL is an upstream address, not an OAuth redirect or browser origin.

The existing API `GET /auth/login` and `/auth/callback` do not provide a Hub login contract. The ORCID request uses a fixed nonce, does not validate `state`, and the callback does not validate an ID token. `GET /auth/apikey` ultimately exposes a year-long API key through a browser flow. The callback also reads a redirect destination from a cookie without an allowlist. These are separate legacy-flow risks, not capabilities the Hub should inherit. Existing API-key clients must continue to work during migration.

ORCID's [sign-in guidelines](https://info.orcid.org/documentation/integration-guide/orcid-oauth-sign-in-guidelines/) add Hub-facing UX requirements: briefly explain why ORCID is used, use a clearly labeled sign-in control with an unmodified ORCID iD icon, and send users to the genuine ORCID page rather than an embedded form or iframe. A normal full-page redirect is sufficient; a popup is optional and must retain a visible ORCID URL. On return, the Hub should clearly indicate that sign-in succeeded and transition to the intended page. The API must derive the Crucible identity from the authenticated ORCID response, never from a manually entered iD. Hub owns the button and transition UI; this API branch does not edit Hub files.

## Recommended first release

Keep the API as the ORCID OAuth client, as the Hub transition document currently assumes, but implement a separate, hardened Hub login flow. Use an established OpenID Connect client library for the ORCID interaction rather than hand-building authorization URLs, token parsing, and ID-token verification. Treat the API-to-Hub handoff as a small first-party one-time exchange, not as an attempt to create a general-purpose OAuth authorization server.

1. Hub creates a login transaction in shared server-side storage, containing random state, PKCE verifier, expected callback, expiry, and a safe relative post-login path. It redirects the browser to an API Hub-login start endpoint with the state and S256 challenge. Do not accept arbitrary redirect URLs.
2. API validates a configured Hub client and exact allowlisted callback, creates its own short-lived ORCID transaction, and redirects to ORCID. Its ORCID transaction has independent random state and nonce, is bound to the browser, and is consumed once. Use ORCID PKCE S256 only after a successful end-to-end enforcement test with a registered client. Otherwise, use the confidential-client code flow with per-transaction OIDC nonce and state binding, as allowed by the OAuth security BCP. The independent API-to-Hub exchange must still enforce its own PKCE S256 challenge.
3. On the ORCID callback, API validates its transaction, ORCID issuer, ID-token signature, audience, expiry, nonce, and subject. Reject callback errors, mismatches, expired transactions, and replays without leaking tokens or raw provider responses. Provision or resolve the human API user using the validated ORCID subject. Never derive identity from a caller-supplied ORCID ID or username.
4. API generates a cryptographically random handoff code, stores only its hash with the user ID, Hub client, original Hub state, PKCE challenge, exact callback, and short expiry, and redirects to that callback with only `code` and `state`. Consume the code atomically once. No API credential, ORCID token, or sensitive profile data appears in the URL.
5. Hub validates its original transaction and state, then exchanges the code server-to-server using Hub client authentication and its PKCE verifier. API validates the stored client, callback, expiry, and S256 verifier before issuing a dedicated, user-scoped Hub API access token and a separate refresh token. Return the user identity, token type, access expiry, and refresh expiry in a typed response with `Cache-Control: no-store`. Do not return an existing year-long API key or mint a platform credential.
6. Hub stores both tokens only in its shared server-side session store, rotates the session ID, and sets a host-only opaque `HttpOnly`, `Secure`, `SameSite=Lax` cookie. Hub makes API calls over HTTPS as the user and refreshes the access token server-to-server when needed. Concurrent Hub requests for one session must share a single refresh operation so they do not reuse an already rotated token.
7. Each refresh requires Hub client authentication and atomically rotates the refresh token while issuing a new access token. Previously issued access tokens may finish their short lifetime so in-flight API requests are not broken, unless the family is revoked. A spent refresh token cannot be used again. Reuse revokes its token family and requires a new login; a lost refresh response may also require a new login. Neither refresh nor normal API activity extends the family's absolute expiry. The Hub session cannot outlive that expiry, and idle sessions expire independently.
8. Logout invalidates the Hub session and revokes the token family, including its active access token. Account disablement and credential revocation must take effect across API replicas within a documented bound. A Hub token must use the same per-resource authorization checks as an ordinary human API key, including current ACL and privilege-mode rules.

Both dedicated Hub tokens should be opaque random values stored hashed at rest and bound to the user, confidential Hub client, and token family, with issued/expiry/revocation timestamps and no service-account authority. Track each refresh generation or its spent hash long enough to detect reuse and revoke the active family. Use a separate token kind or table so legacy API-key rotation cannot unexpectedly replace Hub credentials, and do not apply the existing 60-second positive API-key cache without an explicit revocation policy. These additions require an Alembic revision and a single linear head. The agreed policy is 15-minute access tokens, 30-day absolute refresh-family expiry, 7-day inactivity expiry, and a Hub session that expires no later than the family. These are product policy values, not OAuth-mandated defaults. Hub administrator elevation must not persist merely because the normal session refreshes.

The API uses `HUB_AUTH_CLIENT_ID` (default `crucible-hub`), `HUB_AUTH_CALLBACK_URI` (exact Hub callback), `HUB_AUTH_PUBLIC_API_URL` (public API base URL), and `HUB_AUTH_ORCID_ISSUER` (production or sandbox ORCID). Deployed credentials use pinned `HUB_AUTH_CLIENT_SECRET_VERSION` and `HUB_AUTH_ORCID_CLIENT_SECRET_VERSION` Secret Manager references; local inline secrets remain supported when references are absent. `HUB_AUTH_ORCID_CLIENT_ID` selects the matching ORCID client without changing legacy API-key login. Deployment ConfigMaps initially set `HUB_AUTH_ENABLED=false`. See [deployment credentials and activation](hub_auth_operations.md#deployment-credentials-and-activation). The ORCID callback is `{public API URL}/auth/hub/callback`; register it with ORCID separately from the Hub callback. Never use a Cloud Run upstream URL as a browser callback.

For a local end-to-end test, point the local API at a test database or explicitly approved staging database and configure temporary loopback callback URLs separately from the confirmed production Hub callback. The Hub needs its own shared server-side session store. Production ORCID client credentials require an HTTPS redirect URI; a local self-signed certificate must be trusted by the browser and by the Hub if it calls the HTTPS API. A deployed Hub cannot exchange a code against `127.0.0.1` on a developer machine. Local Hub and API must both be reachable by the same browser and by each other for the code exchange.

New human users are provisioned from the validated ORCID subject. If the ID token omits names, first and last name initially remain blank and the Hub should offer profile completion; a login must not infer identity from a typed ORCID iD or display name. The current user model has no disabled-account field, so account disablement is not implemented by this branch and requires a separate policy before production rollout.

## API contract to publish

- `GET /auth/hub/login`: accepts a registered Hub client identifier, exact registered callback identifier or URI, Hub state, and S256 code challenge; redirects only to the configured ORCID issuer. The exact public URL and input encoding need review against the deployment proxy and base path.
- `GET /auth/hub/callback`: ORCID callback, never a Hub-facing token endpoint. Its success redirects only to a registered Hub callback; errors use a safe generic result.
- `POST /auth/hub/token`: confidential Hub server only. Accepts one-time code, client authentication, registered callback, and PKCE verifier. Returns a typed token response or a generic invalid-grant error. Rate-limit and audit without logging secrets.
- `POST /auth/hub/refresh`: confidential Hub server only. Accepts the active refresh token, rotates the token pair atomically, and returns new typed expiry information. Rejects expired, revoked, or reused tokens; reused tokens revoke the family.
- `POST /auth/hub/revoke`: HTTP Basic confidential Hub client authentication, JSON `token`, and a `204` response with `Cache-Control: no-store`. Revokes all access and refresh generations in that login family, including when supplied a spent refresh token. Unknown tokens, already-revoked families, and tokens belonging to another client return the same `204`; invalid client authentication returns `401`. Other login sessions, legacy API keys, and the ORCID session are unaffected. Already-authorized requests may finish; subsequent authentication checks reject revoked tokens.

### Logout integration

The Hub must snapshot the current refresh token, immediately invalidate its server-side session, clear its session cookie and pending login transaction, reset elevation, then attempt API revocation. Do not wait for successful refresh before revoking: a previously rotated refresh token still identifies the family, and the API serializes refresh and revocation on the family lock. An in-flight refresh must never restore a deleted Hub session.

Logout must be a CSRF-protected POST. Clear browser query caches and notify other tabs without broadcasting credentials; revalidate authentication when a page is restored. If revocation fails, keep the local session deleted and report that API revocation was not confirmed. A bounded server-side retry can use the same token, but must not log it or expose it to the browser. Do not claim successful global logout or sign the user out of ORCID. Logout is session-specific, not an account-wide or all-device revocation feature.

For the Hub integration, the browser starts at `GET /auth/hub/login` with `client_id`, the exact configured `redirect_uri`, random Hub `state`, a S256 `code_challenge`, and `code_challenge_method=S256`. The API callback sends `code` and the original Hub `state` to that exact URI. The Hub validates and consumes its own state before calling `POST /auth/hub/token` with HTTP Basic client authentication and JSON containing `code`, `code_verifier`, and the same `redirect_uri`. Refresh uses HTTP Basic and JSON `refresh_token`; revoke uses HTTP Basic and JSON `token`. Neither the Hub client secret nor the PKCE verifier belongs in a browser URL. The Hub must remove the one-use callback code from browser history after processing.

Document redirects and error outcomes in OpenAPI even where a generated client will handle them as browser navigation. Do not put a client secret, bearer token, ORCID token, or code verifier in logs, tracing, errors, analytics, or URLs. Authorization codes necessarily appear on the registered ORCID and Hub callback URLs; redact them from logs and remove them from browser history after processing. Apply `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on callback and token-bearing responses. Use short, bounded outbound ORCID timeouts and reject unexpected provider redirects.

## Alternatives and non-goals

Hub as the ORCID confidential client is also an established backend-for-frontend pattern and removes the API-to-Hub browser handoff. It would still need an authenticated API exchange of the validated ORCID identity for user-scoped API authority, so it does not eliminate the cross-service trust contract. It also changes the Hub's current API-owned-login decision and requires separate ORCID client registration and user-provisioning ownership. Reconsider it if the team wants Hub to own identity-provider integration long term, but do not switch architectures implicitly.

Using the existing year-long API key in a server-side Hub session would keep it out of JavaScript, but a Hub-session leak would grant a much longer-lived credential, and logout would have to rotate a key that other clients may use. Do not use it for production Hub login. A full OAuth authorization server, ORCID refresh-token storage, browser-held access tokens, and a standing administrator credential in Hub are unnecessary for the first release. The proposed refresh token belongs to Crucible API, not ORCID.

The legacy `/auth/*` and deprecated login aliases should be hardened independently and retained for existing clients until a communicated deprecation. Do not silently redirect old clients into the new Hub flow or alter API-key behavior as part of this feature.

## Verification and rollout gate

ORCID PKCE check on 2026-09-23: both production and sandbox OIDC discovery documents omit `code_challenge_methods_supported`. ORCID's [PKCE feature issue](https://github.com/ORCID/ORCID-Source/issues/5977) was closed in 2022 after the request was captured for prioritization; its comments do not say PKCE was implemented. Current public evidence therefore does not establish support or enforcement. A definitive test requires a registered ORCID client and completed sandbox authorizations: exchange a fresh challenged code with a wrong verifier, another with no verifier, and a third with the correct verifier; require the first two to fail and the third to succeed. Do not run this test against production user accounts or assume that merely accepting a `code_challenge` proves enforcement.

Before staging use, confirm the registered redirect URLs, API and Hub deployment origins, trusted proxy headers, shared transaction/session stores, secret rotation, and account-disable policy. ORCID S256 is not enabled until its enforcement is verified. Write a repository-grounded threat model before production use.

Tests must cover state, nonce, issuer, audience, signature, callback, client authentication, PKCE, expiry, atomic one-use exchange under concurrency, refresh rotation under concurrent requests, spent-token reuse and family revocation, absolute and inactivity expiry, replay, code-injection/login-CSRF, safe redirects, revocation across replicas, logout, account disablement, no browser-visible credential, two-account isolation, ordinary ACL enforcement, and administrator elevation. Confirm existing API-key clients and legacy routes remain compatible. Deploy to staging, pin the checked-in OpenAPI contract for Hub, and collect staging evidence before enabling production login.
