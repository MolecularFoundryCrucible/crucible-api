# Changelog

This changelog records changes that affect API users, operators, or downstream clients. Add entries under `Unreleased` in the same change that modifies the observable contract or operational behavior. Internal-only changes do not require an entry.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and releases follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Batch lookup by MFID: `GET /datasets`, `GET /samples`, `GET /projects`, and `GET /instruments` accept a repeatable `mfid` filter (at most 100 values). Unreadable, missing, and pending-deletion MFIDs are omitted; projects and instruments are found as with an exact slug lookup. `GET /users` accepts repeatable `unique_id` and `username` filters (at most 100 values each).
- `GET /account/recent-resources` items include `identifier`: the instrument's `instrument_id` or the project's `project_id`, null for datasets and samples.
- `affiliation=member` on `GET /datasets`, `GET /samples`, their `/search` and `/facets` routes, and `GET /resources/metadata/search` (where it narrows dataset and sample results only): records the caller reaches through one of their own grants (personal, project, instrument, or group), excluding records visible only because they are public. Combines with `affiliation=owner` (OR) and with `visibility` (for example `affiliation=member&visibility=public` lists public records the caller also has access to). For platform administrators it counts only their own grants. Project list and search keep `affiliation=owner` only.
- Resource capabilities include `can_request_deletion`: whether `POST /resources/{mfid}/delete` would be accepted. For datasets and samples that is contributor access; for projects and instruments it matches `can_delete`; in both cases it is false while a deletion request is already active.
- Added authenticated `GET /print/printers`, listing printers discovered from their retained MQTT status heartbeat with an `online` flag and the last heartbeat time `ts` (printer hostnames and IP addresses are not returned). Only printers that have published at least one status message appear; there is no separate registry of valid `printer_id` values.
- Reworked join requests (design in `docs/join_requests_design.md`). `POST /projects/{project_ref}/join_requests` creates a request (201; 409 `already_member`, `join_request_pending`, `too_many_pending_requests` at 20 pending, or `project_not_accepting_requests` while the project is pending deletion; service accounts get 403). `GET /join_requests` lists with `scope` (`accessible`, `submitted`, `reviewable`), repeatable `status` and `project_mfid`, `requester_id`, `reviewer_id`, `requested_after`/`requested_before`, `reviewed_after`/`reviewed_before`, `q` (requester name, username, or ORCID), `sort` (`request_time`, `review_time`, `status`, `project`, `requester_name`), `direction`, and cursor pagination. `GET /join_requests/facets?field=status|project|requester` counts with the same filters. `PATCH /join_requests/{request_id}` approves at a chosen `role` (default contributor, strictly below the reviewer's own role) or rejects; `POST /join_requests/{request_id}/withdraw` lets the requester withdraw. Items carry `project`, `project_mfid`, `requester` and `reviewer` (public user), `granted_role`, and `capabilities` (`can_review`, `can_withdraw`). Requires migration `c3f1d29a7b64`.
- Added dataset postprocessing pipelines. `GET /pipelines` lists the available pipelines (`carrier_segmentation`, `insitu_aggregation`, `rga_analysis`, `mosaic_stitch`) with a description and a JSON schema of the parameters each accepts. `POST /datasets/{dataset_mfid}/postprocess` with `{"pipeline": ..., "parameters": {...}}` queues a run and returns it (202); it requires contributor access to the dataset, returns 404 for a dataset that is missing, unreadable, or pending deletion, 422 for an unknown pipeline (`unknown_pipeline`) or invalid parameters (`invalid_parameters`), and 503 (`pipeline_unavailable`) when the run cannot be queued, in which case the run is recorded as failed. Every request starts a new run unless it repeats an `Idempotency-Key` header (1 to 128 characters): a retry with the same key from the same caller on the same dataset returns the original run without queueing it again (or queues it again if queueing had failed), and the same key with a different pipeline or parameters returns 409 (`idempotency_key_reused`). `GET /postprocessing_runs` (filters `dataset_mfid`, `pipeline`, `status`) and `GET /postprocessing_runs/{run_id}` show runs on datasets the caller can read; `PATCH /postprocessing_runs/{run_id}` with `status` (`running`, `completed`, `failed`) and `error` lets consumers report progress, requires edit access, and returns 409 (`run_finished`) once a run has completed or failed. Queue messages carry `run_id`, `dataset_mfid`, `pipeline`, `parameters`, and `requested_by`, plus `dsid` for existing consumers. Requires migration `aa8eb05c643d`.
- Added activity tracking. Users record `last_active_at` on any authenticated request (at most hourly), returned to platform administrators and to the user; administrators can filter `GET /users` with `active_since`, `inactive_since`, and `never_active`, and sort by `last_active`. API keys record `last_used_at` (at most every 10 minutes), shown in key status and `GET /account/verify`. Projects and instruments record `last_activity_at` when their datasets, samples, files, metadata, or memberships change (at most hourly); `GET /projects` and `GET /instruments` accept `sort=activity` and `active_since`. Requires migration `b644cf2e7240`; `migrations/data/20261014_backfill_activity_timestamps.py` fills existing users, projects, and instruments.
- Added per-user preferences: `GET /account/preferences` returns the caller's document with an `ETag` (`"p<revision>"`, `"p0"` before the first save), and `PATCH /account/preferences` merges a JSON Merge Patch (RFC 7396; `null` removes a key) with optional `If-Match` (412 `etag_mismatch` returns the current ETag). Shared keys are `theme` (`light`, `dark`, `system`) and `default_record_kind` (`samples`, `datasets`); `hub` is a client namespace object capped at 4 KB, and the document at 16 KB. Unknown keys and invalid values return 422. Available to every authenticated caller, for their own preferences only. Requires migration `5582366c0eb4`.
- Added recently viewed resources: `POST /account/recent-resources` records a view of a resource the caller can read (404 otherwise; repeat views within a minute are not rewritten; the newest 50 are kept), `GET /account/recent-resources?limit=` (1 to 50, default 10) lists them newest first with type, name, and project, filtered by current read access and pending deletions, and `DELETE /account/recent-resources` or `/{resource_mfid}` clears entries. Entries older than 90 days are dropped. The new preference `record_recent_resources: false` turns recording off. Requires migration `d7b51bd885fc`.
- Member and grant entries carry `capabilities` for the caller: `can_remove` (the matching DELETE would succeed, including leaving yourself), `can_change_role` (the matching PATCH or PUT would accept at least one other role), and `assignable_roles` (the roles it would accept). Returned on `GET /projects/{project_ref}/users`, project detail members, instrument members (`include_members`), and `GET /resources/{mfid}/access`; computed by the same rule the routes enforce. Owner entries, owning-project grants, and project grants on projects are fixed (all false).

### Changed

- Settings and secrets are explicit (operator-facing). Secrets come from the environment variable, a file of the same name in the secrets directory (`CRUCIBLE_SECRETS_DIR`, default `/run/secrets` when present), or a full Secret Manager path in `NAME_VERSION`; there are no built-in Secret Manager paths and `GCS_SECRET_STORE` is gone. `.env` is read only from `DB_CONF_FILE` or the working directory. Settings are read with `pydantic-settings`; invalid values and missing required settings stop the server at startup with one message listing them. Required: `DB_SERVER`, `DB_USERNAME`, `DB_DATABASE`, `PGDB_PW`, `CRUCIBLE_SECRET_KEY`; feature settings are required only when the feature is on.
- One way to give each setting (operator-facing): a file named by `NAME_FILE`, a file `NAME` in the secrets directory, or the `NAME` environment variable (secrets also accept `NAME_VERSION`, kept for the Foundry until its platform delivers secrets as files). A setting given more than one way stops the server at startup, naming the setting and the ways found, instead of one way silently winning. Names match regardless of case, and a blank value (empty or only spaces, including an empty file) counts as not given. Every secret follows this, including `HUB_AUTH_CLIENT_SECRET`, `HUB_AUTH_ORCID_CLIENT_SECRET`, `CRUCIBLE_CURSOR_SIGNING_KEY`, and `CRUCIBLE_CURSOR_SIGNING_KEYS`, which could not be files before. With `HUB_AUTH_ENABLED=true`, the startup check requires `HUB_AUTH_CLIENT_SECRET`, `HUB_AUTH_CALLBACK_URI`, and an ORCID client secret (`HUB_AUTH_ORCID_CLIENT_SECRET` or `ORCID_CLIENT_SECRET`). The Secret Manager client is loaded only when a `NAME_VERSION` is used.
- Settings are grouped by area in `app/config.py` (`db`, `security`, `api`, `hub`, `storage`, `ingestion`, `printing`, `proposals`) with no environment variable renamed. The Hub sign-in options, cursor keys, database pool sizes, `EXPECTED_DB_REVISIONS`, `RECORD_BUCKET`, `STORAGE_READ_BUCKETS`, `LEGACY_UPLOAD_TOKEN_DOWNSCOPE`, and `API_CONF_FILE` are now settings: they are read once at startup (changing them needs a restart) and invalid values stop the server instead of being read as defaults or `false`.
- Foundry defaults are removed from the code: RabbitMQ host and user, the MQTT broker, the proposal service URL, the upload bucket, and the GCS project now come only from settings (`RMQ_HOST`, `RMQ_PORT`, `RMQ_USER`, `RMQ_ROUTING_SUFFIX`, `MQTT_HOST`, `MQTT_PORT`, `MQTT_USERNAME`, `PROPOSAL_DB_URL`, `UPLOAD_BUCKET`, `GCS_PROJECT`). The Foundry deployments already set them.
- Printing, ingestion and postprocessing, and proposal sync are switched on by `PRINTING_ENABLED`, `INGESTION_ENABLED`, and `PROPOSAL_SYNC_ENABLED` (default off). When a feature is off its routes answer `501` `{"detail": {"code": "feature_disabled", "feature": ...}}`; `POST /files/{file_id}/ingest` with `status=not_requested` still works. When no upload bucket is configured, storage routes answer `501` `{"detail": {"code": "storage_not_configured"}}`; setting `MULTIPART_UPLOAD_ENABLED` or `STORAGE_READ_BUCKETS` without `UPLOAD_BUCKET`, or `UPLOAD_BUCKET` without `GCS_SA`, stops startup.
- Each server worker reads every secret its enabled features need when it starts (operator-facing), into the same in-memory cache requests use, and refuses to start if one cannot be read (missing, empty, or no access), naming the secret. A bad secret now keeps a new pod out of service during a rollout instead of failing live requests. One reader serves every secret, the Hub's included; each Secret Manager read gives up after 10 seconds instead of retrying for up to a minute, and the Hub client and Hub ORCID secrets must be one line of printable ASCII however they are given (before, only Secret Manager values were checked). Secrets for features that are off (including `GCS_SA` when no bucket is configured) are not fetched from Secret Manager, though the one-way rule still applies to them; `GCS_SA` is now required when `RECORD_BUCKET` is set; the message broker and other services are still contacted only when a request needs them.
- `POST /files/{file_id}/ingest` answers `503` `ingestion_unavailable` and records the request as failed when the message broker cannot be reached, instead of leaving it requested and answering 500.
- The API address can be set without a YAML file (operator-facing): `API_PUBLIC_URL` (scheme and host clients use, for example `http://localhost:8080`), `API_PATH` (for example `api/v3`; empty serves the API at the site root), `ORCID_CLIENT_ID`, and `TRGM_SEARCH_THRESHOLD` (default `0.3`). Environment values win over `API_CONF_FILE`, which is now optional. Browser sign-in redirects work when the API is served at the root.
- The server reads its settings when they are first needed instead of while loading the code, so a missing setting is reported by the startup check with the full list, and tools can load the code without database credentials. The record field `created_with_api_version` uses the same version as `/health` instead of reading `pyproject.toml` from the working directory. An empty `CRUCIBLE_CURSOR_SIGNING_KEY` is treated as unset (cursors are signed with `CRUCIBLE_SECRET_KEY`) instead of signing with an empty key.
- A Docker Compose bundle for running Crucible on one machine (operator-facing), in `deploy/compose/` with its install guide: PostgreSQL 17 with pgvector, a one-time `migrate` service running `db upgrade` that the API waits for, the API, and Caddy in front (plain HTTP on a local port, or automatic HTTPS for a domain name). Secrets are Docker Compose secret files; the API connects as an ordinary database role; the PostgreSQL superuser creates the database and its extensions on first start and is otherwise used only for backups and the database health check. The guide covers the first administrator, connecting nano-crucible, backups and restore, upgrades, other ways to deliver secrets, and using another reverse proxy.
- New installations can create their first administrator (operator-facing): `python -m app.cli admin create` creates a platform administrator (with an MFID, or `--orcid`), their identity group, and an API key, and prints `{"unique_id", "username", "api_key"}` as JSON. In a terminal it asks for missing values and confirms; with `--no-input` or without a terminal, missing required values are an error. It refuses when an administrator already exists unless given `--allow-additional`. Server commands share one entry point, `python -m app.cli` (`db upgrade`, `admin create`).
- New installations can create their database (operator-facing): `python -m app.cli db upgrade` creates the schema in an empty database from a baseline of staging at revision `b8f2d6e41c07` (including the `vector` and `pg_trgm` extensions and the `public` access group) and applies later migrations; on an existing database it applies pending migrations, and it refuses a database with tables but no migration history. Concurrent runs wait for each other. `ALEMBIC_PRODUCTION_DATABASE` names the database the production guard protects (default `crucible`; empty turns it off); `db upgrade` refuses it unless given `--yes-this-is-production`. When `EXPECTED_DB_REVISIONS` is not set, `/health/ready` expects the migration heads of the running code instead of accepting any schema. The image includes `alembic.ini` and `migrations/` (without the one-off scripts in `migrations/data/`).
- The container image listens on `PORT` (default `8000`) with `WEB_CONCURRENCY` workers (default `4`) instead of choosing the port from the build branch, and has the project environment on `PATH`. The Foundry deployments already set `PORT`.

- Security dependency upgrades: FastAPI 0.115.14 to 0.142.4 (Starlette 0.46.2 to 1.7.0), Pillow 11.1.0 to 13.0.0, python-multipart 0.0.20 to 0.0.32, urllib3 2.1.0 to 2.8.0, pg8000 1.31.2 to 1.31.5, prometheus-fastapi-instrumentator 7.1.0 to 8.1.0, and minimum versions for anyio, certifi, idna, Mako and pyasn1 (uv `constraint-dependencies`). python-jose, which has an unpatched critical advisory, is replaced by joserfc for the legacy ORCID session cookie; that cookie now must carry an expiry. OpenAPI `ValidationError` gains the optional `input` and `ctx` fields that FastAPI already returned.
- `GET /resources/{mfid}/access` and `GET /instruments/{instrument_ref}/service_accounts` are readable by anyone holding a role on the resource other than through public access (directly or through a project grant), and by platform administrators in elevated mode; previously both required admin. Access that comes only from public visibility still returns 403. Entries are read-only for callers who cannot manage access: grant `capabilities` are all false, and operator entries now carry `capabilities` with `can_remove` true only for instrument admins. Resource `capabilities` gain `can_view_access`. Changing grants and operator bindings still requires admin.
- `GET /users/search` returns the shared paginated envelope (`limit`, `items`) like the other search routes instead of a bare array. Clients that read the body as an array must read `items`; nano-crucible 3.0.0 and later already do.
- `GET /users` returns `user_capabilities` on every item, not only on exact lookups, and platform administrators receive `api_key_status` on every item that has a key.
- File identity rules from PR #335 (Peter Doak). `POST /datasets/{dataset_mfid}/files` also compares `storage_backend` when a filename is repeated (a retry ignores `storage_path` and `access_note`). Non-GCS filenames must be canonical relative POSIX paths (422 otherwise), and the database enforces that and per-dataset uniqueness for non-GCS records (migration `b8f2d6e41c07`, which stops if existing non-GCS rows violate either, and adds the constraints `NOT VALID` then validates them and builds the index concurrently, so it does not block reads or writes). `PATCH /files/{file_id}` returns 409 `filename_immutable` when renaming a non-GCS file, 409 `storage_backend_class_change` when moving a record between GCS and non-GCS (previously allowed for legacy GCS records without a stored generation), and 409 `filename_exists` when renaming onto a filename already in the dataset.
- Project and instrument deletion compute the deletion summary once per request instead of twice (request creation reused nothing between the blocker check and the preview; approval and forced deletion recomputed it inside the hard delete and discarded it). `POST /datasets/{dataset_mfid}/files` no longer loads all of the dataset's file records to add one.
- PATCH routes reject `null` (422) for fields that cannot be empty, instead of returning 500 from the database: `sample_name` (`PATCH /samples/{sample_mfid}`), `project_id` and `organization` (`PATCH /projects/{project_ref}`), `first_name` and `last_name` (`PATCH /account/profile`, `PATCH /users/{user_ref}`), and `filename`, `storage_backend`, `size`, and `sha256_hash` (`PATCH /files/{file_id}`). Leaving a field out still leaves it unchanged; `sample_name`, `organization`, `first_name`, and `last_name` are trimmed and must not be blank. OpenAPI now types these fields as non-nullable; fields that can be cleared (for example `description`, `title`, `email`, `username`, `access_note`) still accept `null`.
- Upgraded Pydantic from 2.13.3 to 2.14.1 (`pydantic>=2.14,<3` is now a direct dependency).
- One rule for granting access: you may grant, change, or remove a role at most your own, for project membership (`POST`, `PATCH`, and `DELETE /projects/{project_ref}/users/{user_ref}`, join request approval) as well as resource grants. Editors can now add editors, admins can add admins, and members at or above editor can remove members up to their own role; the owner still changes only through `POST /resources/{mfid}/transfer_ownership`.
- Datasets and samples store only `project_mfid` and `instrument_mfid`; `project_id`, `instrument_id`, and `instrument_name` in responses always come from the current project and instrument. A dataset without a registered instrument now shows `instrument_id`, `instrument_name`, and `instrument` as null instead of its stored free-text name, the `instrument_name` list filter matches only registered instruments, and `previous_instrument_name` from `PUT /datasets/{dataset_mfid}/instrument` is the previous registered instrument's name. Record files in the record bucket carry `project_mfid` and `instrument_mfid` instead of `project_id` and `instrument_name`.
- Dataset and sample `owner_orcid` are indexed, so owner filters (`owner_id`) and owner facets no longer scan the whole table (about 50 ms to about 1 ms on production for a dataset owner filter). Requires migration `5be2f0c8d4a1`, which builds the indexes concurrently without locking the tables.
- Timestamps are UTC. Time filters (`creation_time_*`, `modification_time_*`, `active_since`, `inactive_since`, and the join request `requested_*` and `reviewed_*` filters) treat a value without an offset as UTC and convert values with an offset to UTC; values without an offset were rejected with 422 on most routes and interpreted in the database session's timezone on the activity filters. Timestamp fields in responses (activity, API key use, preferences, recent resources, join requests, postprocessing runs, multipart expiry, Hub token expiry) are written as UTC with a `Z` suffix and microseconds. Clients convert to local time for display.
- `POST /datasets/{parent_dataset_mfid}/children/{child_dataset_mfid}` and `POST /samples/{parent_sample_mfid}/children/{child_sample_mfid}` reject linking a record to itself (422 `self_link`) and links that would make lineage cyclic, where the child is already an ancestor of the parent (409 `lineage_cycle`). The check follows every link, including through records the caller cannot read, without naming them. Re-posting a link that already exists is unaffected.
- `GET /entity_graph_cte/{entity_mfid}` returns `relationship_type` on parent/child edges (`null` for sample-dataset associations), as `GET /project_graph/{project_ref}` already did, and recursive graphs are much faster: the traversal now checks access only for the records it reaches, instead of evaluating it for every sample and dataset first (about 1 s to under 25 ms of database time for an administrator on production). Nodes and edges are unchanged.
- Join requests are reviewed by project editors and above (and platform administrators), the same people who can add members directly; before, only project owners could. A request is visible only to its requester, its reviewers, and platform administrators (404 otherwise). Adding someone to a project by any route closes their pending request there as approved. `request_time` and `review_time` are timestamps, and `status` can now also be `withdrawn`.
- `GET /health/ready` stays ready when the database schema is ahead of the running build (newer additive migrations applied before a deploy) and reports `database.schema_state` (`current`, `ahead`, `behind`, `mismatch`); it is not ready only when a migration the build needs is missing. Running a migration before its deploy no longer takes the old pods out of service. The image now includes `migrations/versions/` to tell the cases apart.
- Successful `/health`, `/health/live`, `/health/ready`, and `/metrics` requests are no longer written to the request log (failures still are), and these routes are excluded from the HTTP request metrics.
- Request log lines now end with `actor=<user id> credential=<api_key|hub>` (`actor=- credential=-` for unauthenticated requests), so a request can be traced to its caller.
- Multipart upload sessions now choose their part size from the file size: the size divided by 8, rounded up to a whole MiB, between 8 MiB and 64 MiB, so files up to 512 MiB upload as about 8 parallel parts instead of one 64 MiB part. The size is returned as `part_size` from initiation and status, as before; clients must plan parts from it rather than assume 64 MiB. Sessions already in progress keep their size.
- Filenames are unique within a dataset for `POST /datasets/{dataset_mfid}/files`. Repeating a filename with the same `sha256_hash` and `size` returns the existing record; repeating it with different content returns 409 `filename_exists` with `file_mfid` and `etag` (the same shape as multipart initiate), instead of adding a second record with that name. Clients that want to overwrite update the existing file: `PATCH /files/{file_mfid}` for remote files, or `POST /files/{file_mfid}/upload/multipart/initiate` for GCS files. A matching hash under a different filename now creates a new record instead of returning the record with the other name.
- Datasets and samples with a pending or approved deletion request follow one contract (`docs/database_deletion_contract.md`). Exact lookups still work (detail, files, file detail and download link, ingestion requests and postprocessing runs by id). Lists, filters, and traversals hide them: `GET /files`, `GET /ingestion_requests`, and `GET /postprocessing_runs` omit them; `GET /datasets?sample_mfid=`, `GET /ingestion_requests?dataset_mfid=` or `?file_mfid=`, `GET /datasets/{dataset_mfid}/parents`, `/children`, `/samples`, and `GET /samples/{sample_mfid}/children` return 404 for them. Writes return 409 with `{"code": "pending_deletion", "status", "message"}`: adding files and thumbnails, every upload path including multipart replace and completion (`dataset_pending_deletion`), `PATCH` and `DELETE /files/{file_id}`, ingestion and postprocessing requests (postprocessing returned 404 before), and creating links. The existing 409 for assigning to a project or instrument pending deletion now uses the same structured detail. Status updates on ingestion requests and postprocessing runs stay allowed. `GET /files/{file_id}` and `GET /ingestion_requests/{request_id}` return 404 instead of 403 when the caller cannot read the dataset, as does `GET /ingestion_requests?dataset_mfid=` for an unreadable dataset.

### Deprecated

- `POST /users/resolve`: use `GET /users` with repeatable `unique_id` or `username`, or an exact `email`. Responses carry a `Deprecation` header.
- The `unique_id` filter on `GET /datasets` and `GET /samples`: use `mfid`. It now accepts repeated values like `mfid`, and requests using it carry a `Deprecation` header.
- `GET /users/{user_ref}/apikey/verify`, which returns `Deprecation: @1792368000`. Administrators get the same status as `api_key_status` from `GET /users/{user_ref}`; callers checking their own key use `GET /account/verify`.
- `POST /access_groups/{group_name}/join` is deprecated in favor of `POST /projects/{project_ref}/join_requests`, and `GET /account/join_requests` in favor of `GET /join_requests?scope=submitted`. The `group_name` field and query parameter of join requests are deprecated in favor of `project` and `project_mfid`.
- `POST /datasets/{dataset_mfid}/carrier_segmentation`, `/insitu_spec_aggregation`, `/rga_analysis`, and `/mosaic_stitch` are deprecated in favor of `POST /datasets/{dataset_mfid}/postprocess`. They now start a tracked postprocessing run and return it instead of an empty body.

### Removed

- Removed the stale `requirements.txt`; install from `uv.lock` (`uv sync --locked`), as the Docker image already does.
- Removed the deprecated `GET /users/me` (use `GET /account/profile`), `PATCH /users/me` (use `PATCH /account/profile`), and `GET /samples/{sample_mfid}/datasets` (use `GET /datasets?sample_mfid=`). None had production calls in the 60 days before removal; `PATCH /users/me` skipped the username and email availability checks and `GET /samples/{sample_mfid}/datasets` turned arbitrary query parameters into column filters, both returning 500 on some inputs.
- Removed nine unused legacy graph routes: `GET /entity_graph/{entity_mfid}`, `/entity_graph_bfs/{entity_mfid}`, `/datasets/{dataset_mfid}/dataset_graph` and `/dataset_graph_cte`, `/samples/{sample_mfid}/sample_graph` and `/sample_graph_cte`, and `/projects/{project_ref}/sample_graph`, `/dataset_graph`, and `/entity_graph`. None was called after 2026-08-01, and several traversed through, or returned the MFIDs of, datasets and samples the caller could not read. Use `GET /resources/{resource_mfid}/graph`, `GET /entity_graph_cte/{entity_mfid}`, or `GET /project_graph/{project_ref}`.
- Removed `POST /extract_metadata`, the unused route that extracted metadata from notebook images with an AI model. It let any authenticated caller choose the URL the server connected to (`api_url`), which allowed requests to internal services. The `anthropic` dependency is removed with it.
- Direct API ORCID sign-in (`/auth/login`, `/auth/callback`) now reads `ORCID_CLIENT_ID` (falling back to `orcid_client_id` in `API_CONF_FILE`) and `ORCID_CLIENT_SECRET` / `ORCID_CLIENT_SECRET_VERSION` (replacing `CLIENT_SECRET` and the hardcoded Secret Manager path) from the environment; `main` and `staging` Kubernetes ConfigMaps and Deployments now set `ORCID_CLIENT_ID` and `ORCID_CLIENT_SECRET_VERSION` explicitly.

### Fixed

- OpenAPI now documents what 21 operations actually return. The ORCID sign-in redirects (`GET /auth/login`, `/auth/callback`, and deprecated `/login`, `/auth`) are documented as 307 redirects; `GET /auth/apikey` (and `/user_apikey`) as JSON `{crucible_apikey}` or an HTML email prompt, or a 307 to sign-in; `/metrics` as `text/plain`. Routes that returned untyped JSON now declare response models: `{message}` for the unlink routes and `DELETE /files/{file_id}`, `{detail}` for the access-revocation routes and the deprecated access-group removal, `{url, expires_in}` for `GET /files/{file_id}/download_link`, a map of file MFID to URL for `GET /datasets/{dataset_mfid}/download_links`, the deletion preview or `{detail}` for `DELETE /resources/{mfid}`, `ApiKeyRead` for the key regeneration routes, and a typed graph for `GET /entity_graph_cte/{entity_mfid}` and `GET /project_graph/{project_ref}`. Response bodies are unchanged.
- Three concurrency races. A multipart upload completing while its dataset is hard-deleted returned 500 and could leave the assembled object in storage; it now returns 409 (`dataset_deleted`) and removes the object. Concurrent `POST`/`PATCH /resources/{mfid}/metadata` on the same record could lose one update or fail with 500 on the first insert; writes to one record's metadata are now serialized. A deletion request on a project or instrument could pass its blocker check while a dataset or sample was being assigned to it; assignment now share-locks the parent, so one of the two waits and the assignment gets 409 `pending_deletion`.
- The SQLModel definitions now declare the same unique indexes production has: the partial unique `ix_user_username` and `ix_instrument_instrument_id` (where the column is not null) and the `scientific_metadata_new_unique_id_key` unique constraint. Tests built from the models now enforce them, and autogenerated migrations no longer propose changing them. No database change.
- Storage errors no longer leak provider details (bucket URLs, service-account emails) into responses. Download links and legacy upload initiation return 503 with a fixed message and log the cause; `POST /datasets/{dataset_mfid}/upload/complete` returns 422 "Uploaded file not found in storage" when the object is missing and 503 for other storage failures (it returned 422 with the raw error for both).
- `POST /users` resolves `project_ids` like every other project reference: an MFID or a case-insensitive `project_id`, with duplicates counted once. A wrong-case slug or an MFID no longer returns a false 404. A requested project with an active deletion request returns 409 `pending_deletion` before the user is created; proposal-discovered projects that are unknown or pending deletion are skipped with a warning.
- `GET /deletion_requests` returned `null` `project_id` and `project_mfid` for project deletion requests, left them out of `?project_mfid=` for that project, and sorted them as projectless under `sort=project_id`; they now report their own project, as `GET /deletion_requests/{request_id}` and the create response already did.
- `POST /datasets/{dataset_mfid}/samples/{sample_mfid}` returned 500 after creating the link when the dataset has no name; `dataset_name` is now nullable in the response, as in other dataset responses.
- `GET /users/{user_ref}/apikey/verify` returned 500 for keys stored with a full timestamp (every key issued by current code); it now reports the same status as `api_key_status`.
- Project roles could be granted outside membership: `PUT /resources/{project_mfid}/access/users|projects/...` gave a project role that bypassed the membership rules, did not appear among the project's members, and survived removal from the project. These routes, their `DELETE` forms, and `POST /resources/{project_mfid}/access_groups` now return 409 `use_project_members`. Changing or revoking a dataset or sample's grant for its own project returns 409 `owning_project_grant`; it follows `POST /resources/{mfid}/project`. Sharing records with other projects is unchanged.
- Renaming a project (`PATCH /projects/{project_ref}` with a new `project_id`) failed with 500 for every project, because legacy slug columns on datasets and project memberships still referenced the old slug. Datasets, samples, and memberships now link to projects only by MFID, so a rename changes only the project row, and moving a record of a renamed project to another project no longer returns 422. Requires migration `9d41c6a2e7f3`.
- The legacy ORCID sign-in routes (`/login`, `/auth`, `/user_apikey`, `/regenerate_apikey`, and their `/auth/*` forms) redirect to sign-in again instead of returning 500 when the short-lived sign-in token is missing, expired, or invalid; return only to a local path after sign-in, never to another site named in the return-page cookie; and time out ORCID calls after 10 seconds with 502 instead of holding a worker.

- Staging wrote its record files (`{mfid}/record.json` and `metadata.json`) into the production record bucket, where a staging edit to a record copied from production would overwrite that record's production copy and revision. The bucket now comes from the `RECORD_BUCKET` setting: `mf-record-prod` on main and the new `mf-record-staging` on staging; record files are skipped, with a warning, when it is unset.
- `GET /account/join_requests` returned 500 for anyone who had made a join request, and join request lists returned 500 when a request's project no longer existed.
- Uploading a new file (signed multipart or legacy `/upload/complete`) now updates the dataset's `modification_time`, and with it the project's and instrument's `last_activity_at`; only replacements did before.
- An upload whose content matches a file already in the dataset under a different name is now stored as a new file. Before, initiation returned the existing file of the other name and never created the requested one, and it also skipped the `filename_exists` conflict when the requested name was taken by different content. Initiation still returns the existing file when both the name and the content match.
- Locating the stored object for an old file record without a `storage_path` now requires the whole file name to match (`bar.tif` no longer matches `foobar.tif`), prefers `{dataset_mfid}/{filename}`, and returns 409 instead of guessing when several objects match.

- The dataset processing routes (`carrier_segmentation`, `insitu_spec_aggregation`, `rga_analysis`, `mosaic_stitch`) required only a login: any authenticated caller could queue jobs on any dataset, including private datasets, datasets pending deletion, and MFIDs that do not exist. - JSON request bodies nested too deeply to parse (thousands of levels) return 422 (`type: json_too_deep`) instead of 500.
- JSON request bodies that PostgreSQL cannot store, or that are not valid I-JSON (RFC 7493), are rejected with 422 instead of failing with 500, with one entry per location (up to 20): NUL characters (`\u0000`), unpaired UTF-16 surrogates, and Unicode noncharacters in any key or string (`type: unsupported_character`), and the non-standard number literals `NaN`, `Infinity`, and `-Infinity` (`type: invalid_number`; send `null` for a missing value). - `If-Match` on `PATCH /account/preferences` and `POST /files/{file_mfid}/upload/multipart/initiate` now ignores a `W/` prefix and accepts a comma-separated list. Cloudflare weakens ETags on compressed responses, so clients echoing the received ETag got 412 on every write.

- Dataset responses now resolve `instrument_name` from the assigned instrument through `instrument_mfid`, so instrument renames are reflected immediately. Datasets without a registered instrument keep their stored label. Generic dataset PATCH accepts either the stored label or the current name as the unchanged value.
- Deprecated the `instrument_name` lookup on `POST /datasets` and the `instrument_name` filter on `GET /datasets`. The filter now matches the displayed name. Use `instrument_id` or `instrument_mfid`.
- `project_id` no longer has to differ from instrument display names.
- Instrument creation no longer grants the instrument operator group `editor` on the instrument record. `migrations/data/20261005_remove_instrument_group_record_grants.py` removes the grant from existing instruments.
- Deprecated `POST /users/{user_ref}/access_groups/{group_name}` now rejects human users for instrument groups with 409. Instrument groups hold service accounts only.
- Production readiness now expects database revision `f3b7c2a91d04`.
- `GET /ingestion_requests` now returns the authorization-filtered collection for any caller with viewer access to the parent datasets; non-administrators no longer need to supply a dataset or file filter.
- Deletion-request responses now require caller capabilities, statuses and review decisions use documented enums, and collection ordering uses descending request time and request ID.
- Authenticated responses now use private caching, and elevated responses use `Cache-Control: private, no-store`. Omitted privilege mode preserves existing platform-administrator behavior.
- Added `platform_role=contributor` for platform-wide read and create access without administrator authority. New service accounts receive this role by default and may use `accessible_to_user` for project, sample, and dataset collections. `is_service_account` remains an identity discriminator, and non-admin service accounts are capped at contributor even when an ACL or group standing would otherwise grant a higher role.
- Removed legacy group-based administrator and resource-permission fallbacks. Platform administration now requires `platform_role=admin`, and project and instrument authorization now requires canonical resource ACLs.
- Project membership routes now reject editor, admin, and owner roles for non-admin service accounts instead of storing roles that their authorization ceiling cannot use.
- API responses containing API keys now send `Cache-Control: no-store` on account, administrator, service-account creation, and key-rotation routes.
- Initial metadata creation, associated-file creation, upload initiation and completion, keyword association, ingestion-request creation, and same-project resource linking now require contributor access. Repeated associated-file creation returns the existing record without updating it.
- Associated-file creation now accepts `storage_path` for non-GCS catalog-only files so their location can be registered atomically.
- Dataset, sample, instrument, and project collection, search, and singleton queries now reject unknown parameters with 422. The generic resource singleton follows the same rule. Previously working exact dataset, sample, and instrument filters remain explicit and deprecated where appropriate.
- Dataset and sample pagination preserves the legacy behavior in which cursor takes precedence when cursor and offset are supplied together.
- Signed continuation cursors now use a compact internal Protobuf payload containing only page position. Request filters, ordering, resource type, and caller identity remain bound through the HMAC signature without being exposed in the token.
- API-owned resource creation and modification timestamps now use timezone-aware database columns, canonical UTC `Z` responses, database-generated values, immutable creation times, and automatically advanced modification times. Migration revision `8c4f2a1d7e60` converts approved legacy formats using the documented Pacific-time policy, converts empty and `NaN` sentinels to null, and rejects unsupported values. Revision `3f2b6a9c1d84` adds database enforcement. The producer-supplied dataset `timestamp` field is unchanged.
- Deployment readiness now reports degraded status when the connected database revision differs from `EXPECTED_DB_REVISIONS`.
- Trigram searches now normalize bounded input, treat prefix wildcard characters literally, bind the request-local similarity threshold, and use canonical unique IDs as deterministic relevance tie-breakers.
- Dataset, sample, instrument, and generic resource singleton GETs now resolve the public-safe owner object by default. Pass `include_owner=false` to omit it. Collection and search expansion remains opt-in.
- Large bulk first-thumbnail lookups now emit a structured operator warning above a configurable threshold without rejecting the request, and duplicate identifiers are removed before querying.
- Thumbnail uploads now release their database connection during image processing and recheck edit authorization before writing.
- Concurrent thumbnail uploads to the same dataset now serialize their dataset-scoped idempotency check, preventing identical requests from creating duplicate rows.
- Deletion-request and join-request collections now resolve project information in their page queries instead of issuing per-item queries. File detail responses reuse the already authorized dataset instead of lazily loading it again.
- Project membership now follows a strict hierarchy: editors manage contributor and viewer roles, admins manage editor and below, and owners manage admin and below. Project capabilities report the corresponding lower `max_grant_role`.
- Canonical and generic resource detail reads now share service loaders. `GET /resources/{mfid}` mirrors canonical authorization semantics and avoids unnecessary deletion-request work for projects and instruments.
- Instrument display names now preserve caller-supplied casing instead of being forced to lowercase.
- Instrument collection filters and dataset assignment by `instrument_id` now resolve case-insensitively.
- Instrument search accepts an optional `status` filter with `active`, `maintenance`, and `decommissioned` values. Omitting it preserves the existing all-status search behavior.
- Project membership mutation routes now accept named roles (`viewer`, `contributor`, `editor`, `admin`, and `owner`) instead of integer enum values. `owner` remains rejected with 409 and requires the ownership-transfer route.
- Service accounts may no longer register instruments, including when they hold platform-admin status. Human platform administrators may continue registering an instrument for another identity.

### Deprecated

- Reading an existing API key through `GET /account/apikey` and `POST /users/{user_ref}/apikey`. Both still work for API-key callers and return `Deprecation: @1791763200`; use the regenerate routes, which keep working once keys are stored hashed.
- The `email` and `username` query parameters on `POST` and `DELETE /projects/{project_ref}/users/{user_ref}`. Put the username in the path instead.
- Email in `{user_ref}` path segments. It still resolves, but emails in URLs are written to access logs; use the ORCID, MFID, or username.
- `GET /users/by-username/{username}`. Use `GET /users/{user_ref}`.
- `ThumbnailRead.dataset_id` (internal integer key) in favor of `dataset_mfid`, and `dataset_id` and `sample_id` on the dataset-sample link response in favor of `dataset_mfid` and `sample_mfid`.
- The `resource_id` fields on `TransferOwnershipRead`, `DeletionRequestRead`, and `DeletionPreviewRead`, and on dataset, sample, instrument, and project detail `deletion_request` objects, in favor of the new `resource_mfid` twin. Both fields are returned with identical values.
- The `dataset_id` and `file_id` filters on `GET /ingestion_requests` in favor of `dataset_mfid` and `file_mfid`. Both accept the same MFID values.
- Undeclared `GET /users` query parameters are now ignored instead of being applied as user-attribute filters. Affected responses carry `Deprecation: @1799280000` and name the ignored parameters in the server log; the parameters will be rejected with 422 at that announced date. No `Sunset` header is sent.

### Security

- GCS file downloads (`GET /files/{file_id}/download_link`, `GET /datasets/{dataset_mfid}/download_links`) and ingestion requests now serve only objects in an allowed bucket (`UPLOAD_BUCKET`, `MULTIPART_UPLOAD_BUCKET`, or `STORAGE_READ_BUCKETS`) under the file's own dataset (`{dataset_mfid}/...`). Previously a caller with EDIT on a dataset could point a file record's `storage_path` at any object or bucket in the project through `PATCH /files/{file_id}` and download it. A record outside the rule returns 409 with `{"detail": {"code": "storage_location_invalid", "reason": ..., "message": "File storage location is not valid: <reason>"}}` and is `null` in bulk links. A read-only audit (`migrations/data/20261013_audit_file_storage_paths.py`) found no production record falls outside the rule; the 229 staging test records under the retired `uploads/` multipart layout now return 409. A multipart object without a recorded generation now returns 409 instead of 403 on download and ingestion.
- `PATCH /files/{file_id}` returns 422 when it would set a GCS file's `storage_path`, switch a record with a path to the `gcs` backend, or change a GCS file's `size` or `sha256_hash`. Echoing current values, clearing the path, and all edits to non-GCS catalog records are unchanged.
- The access token returned by `POST /datasets/{dataset_mfid}/upload/initiate/multipart` is now downscoped with a Credential Access Boundary to objects under `{dataset_mfid}/` in the upload bucket (`roles/storage.objectAdmin` within that prefix). Parallel uploads, overwrites of the dataset's own files, and reading them back keep working; the token can no longer read, write, delete, or list objects of other datasets or multipart objects under `{dataset_mfid}/_files/`. The response shape is unchanged. Minting now calls Google STS, so the API needs egress to `sts.googleapis.com`; if the exchange fails the route returns 503 and never falls back to the broad token. Setting `LEGACY_UPLOAD_TOKEN_DOWNSCOPE=false` restores the previous service-account token as an emergency rollback.
- Hub sessions can no longer read existing API keys: `GET /account/apikey` returns 403 `api_key_read_not_allowed`, and `POST /users/{user_ref}/apikey` returns 409 `api_key_exists` instead of the existing key.
- Creating an API key from a Hub session (regenerate routes, `POST /users/{user_ref}/apikey`, `POST /service_accounts`, `POST /service_accounts/{service_account_ref}/rotate_key`) requires an ORCID sign-in within the last 600 seconds, otherwise the API returns the RFC 9470 step-up challenge (401, `WWW-Authenticate: Bearer error="insufficient_user_authentication"`). API-key callers are unaffected.
- Hub sessions default to normal privilege mode when `Crucible-Privilege-Mode` is omitted; API keys keep the elevated compatibility default for administrators.
- `HUB_AUTH_ENABLED` now defaults to `false` when unset.
- Hub authentication logs redact validation failures and unexpected errors, and every Hub authentication response sends `Cache-Control: no-store`.
- `HUB_AUTH_CALLBACK_URI` accepts a comma-separated list of exact Hub callbacks; every entry must be HTTPS or an HTTP loopback address. Staging now enables Hub sign-in in its checked-in configuration with the local development callback `http://localhost:3000/hub/auth/callback`.
- User email addresses are now unique, compared case-insensitively after trimming whitespace (migration `e5a1c8d93f27`, after auditing existing data with `migrations/data/20261012_audit_user_emails.py`). `PATCH /account/profile`, `PATCH /users/{user_ref}`, and `POST /users` return 409 without identifying the other account, so an address can no longer be claimed by a second account and redirect email-based member additions or access grants. Blank emails are stored as null. Emails remain optional and unverified.
- Username and email conflicts now return a structured 409 detail, `{"code": "already_in_use", "fields": [...], "message": ...}`, listing every conflicting field, instead of the plain string `Username already taken`. Clients that print `detail` still show the message.
- Non-administrators can no longer filter users by `platform_role`; the filter is administrator-only and other callers receive 403.
- Removed the generic `GET /users` loop that turned any undeclared query parameter matching a `User` attribute into a filter, which let callers probe arbitrary columns including internal ones.

### Fixed

- `GET /users/{user_ref}/projects` now hides projects with a pending or approved deletion request, matching `GET /projects`.
- Legacy upload initiation and `POST /datasets/{dataset_mfid}/files` no longer deduplicate against multipart files whose SHA-256 is an unverified client claim, and no longer return 500 when several files share a hash. Both, and legacy upload completion, now return 409 for a filename reserved by an active multipart upload instead of making that upload fail at publication.
- Part URLs within a multipart signing batch are signed concurrently.
- `POST /datasets` with an `instrument_name` shared by more than one instrument now returns 409 instead of a server error.
- Permanent dataset and sample deletion now removes associated resource embeddings instead of failing with a foreign-key violation.
- Escaped profile values in the legacy API-key page and removed dynamic values from its inline JavaScript.
- Disabled raw Uvicorn access logs while retaining API request logs without query strings.
- Deletion-request submitters can now read their own request detail without receiving deletion-review authority.
- Identical thumbnail images uploaded to different datasets now remain independently owned instead of moving an existing thumbnail between datasets.
- Thumbnail uploads now verify dataset edit access before decoding or processing image data.
- Thumbnail deletion now applies dataset edit authorization in its initial lookup, consistently returning 404 for absent or inaccessible datasets and avoiding a redundant permission query.
- Thumbnail uploads now strictly validate base64 input and return stable errors without exposing image-library exception details.
- Thumbnail normalization now enforces configurable 50 MiB and 50 megapixel source limits, applies EXIF orientation, uses the first animation frame, composites transparency onto white, and accepts common raster formats only.
- Dataset thumbnail lists are now ordered by thumbnail ID, matching the bulk endpoint's definition of the first thumbnail.
- Join-request review now locks the pending request during its state transition, and the database prevents concurrent duplicate pending requests for the same user and access group.
- Project results from `GET /resources/metadata/search` now resolve titles through the canonical project MFID instead of the legacy project slug.
- Instrument updates now reject explicit null values for required identifiers, names, and locations with 422 instead of failing during persistence.
- Repeating a project add-member request with the member's current role remains idempotent, while requesting a different role now returns 409 and directs the caller to the role-update route instead of silently ignoring the requested change.
