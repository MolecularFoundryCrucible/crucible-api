# Upgrading from 3.3.1 to 4.0.0

Releases before 4.0.0 were deployed only by the Molecular Foundry and by evaluation installations of the Docker Compose bundle. This guide covers those deployments and the client applications written against 3.3.1.

All routes remain under `/api/v3`. This is a major release because the API now performs user authentication itself, the previous methods of obtaining an API key are removed, and the container image and its settings have changed.

| Audience | Section |
|---|---|
| Operators of a Kubernetes deployment (the Molecular Foundry) | [Kubernetes](#kubernetes) |
| Operators of the Docker Compose bundle | [Docker Compose](#docker-compose) |
| Authors of client applications | [Client authors](#client-authors) |
| Contributors to this repository | [Developers](#developers-of-this-repository) |

## Release order

Deploy API 4.0.0 first, then Hub 1.8.0 and nano-crucible 4.0, within a single maintenance window.

| Combination | What breaks |
|---|---|
| Hub 1.7.x on API 4.0.0 | The key buttons (regenerate, provision, rotate) return 410. Sign-in works. |
| Hub 1.8.0 on API 3.3.1 | Does not work. |
| nano-crucible 3.3.0 on API 4.0.0 | `account api-key` returns 410 and the `/user_apikey` link is removed. Uploads work only where `MULTIPART_UPLOAD_ENABLED=true`. All other functions work. |
| nano-crucible before 3.3.0 on API 4.0.0 | Cannot upload files. |
| Crucible Lens before its new sign-in | Cannot sign in. |

## Kubernetes

### 1. Before deploying the new image

Complete these steps while 3.3.1 is running. None of them changes the behavior of 3.3.1.

- [ ] Set `API_PUBLIC_URL` (for example `https://crucible.lbl.gov`) and `API_PATH` (for example `api/v3`) on the API Deployment.
- [ ] Set `CRUCIBLE_AUTH_PROVIDERS` with the ORCID entry, keeping `"legacy_callback": true`. Fields: [the provider list](../sign_in_operations.md#the-provider-list).
- [ ] Provide that provider's secret as `OIDC_ORCID_CLIENT_SECRET` (or its `_VERSION`).
- [ ] Leave the `HUB_AUTH_*` settings unchanged. Do not add `CRUCIBLE_AUTH_CLIENTS` yet.
- [ ] Leave the password settings unset to keep ORCID as the only identity provider.
- [ ] If the root filesystem is read-only, mount an `emptyDir` on `/tmp` and on `/dev/shm`.
- [ ] Run `python -m app.cli settings check` in the deployment pipeline without `-w /root`.
- [ ] Apply the reverse proxy's sign-in rate limits to `/api/v3/oauth/*` in addition to `/api/v3/auth/hub/*`.
- [ ] Verify that `CRUCIBLE_SECRET_KEY` (and the cursor signing keys, if set) has at least 32 characters; 4.0.0 refuses to start with a shorter key. Replacing it interrupts sign-ins in progress and invalidates list cursors, but not sessions or API keys.
- [ ] Verify that `MULTIPART_UPLOAD_ENABLED=true`: the older upload routes are removed, so multipart is the only upload method.
- [ ] Set `FORWARDED_ALLOW_IPS` to the addresses from which the API sees its proxies, and configure the reverse proxy to set `X-Forwarded-For` to the client address instead of appending to it. Without both, all clients share the same attempt limits. See `FORWARDED_ALLOW_IPS` in [Authentication configuration](../sign_in_operations.md).
- [ ] Configure the reverse proxy to return 404 for `/api/v3/metrics`; the API serves it without authentication.
- [ ] Optional: set `RESERVED_PROJECT_ID_PATTERN` to the naming scheme of proposal projects (the Molecular Foundry: `MFP[0-9]{5}`), so that only administrators create or rename such projects and proposal sync is limited to them.
- [ ] Update deployment assertions (expected settings, expected database revision `9d4a2c7e6f13`).

### 2. Cut-over

- [ ] Back up the database.
- [ ] Run `python -m app.cli db upgrade`. Rerun it if a migration times out waiting for a lock.
- [ ] Deploy the API 4.0.0 image. `GET /health/ready` reports the version and `schema_state: current`.
- [ ] Verify the instrument grants from inside the pod: `python -m app.cli instruments check` prints only zeros. If not, rows written by 3.3.1 between the migration and the deploy remain; run `python -m app.cli instruments check --commit`. The migration has made each instrument's owner, admins and editors members of the instrument, so they now read its datasets.
- [ ] Record the logins of all users, from inside the pod. The first command only reports:

  ```bash
  python -m app.cli identity backfill --issuer https://orcid.org
  python -m app.cli identity backfill --issuer https://orcid.org --commit
  ```

- [ ] Set `CRUCIBLE_AUTH_IDENTITY_LOOKUP=true` and restart.
- [ ] Fill the owners of datasets and samples written by 3.x, from inside the pod. Until then the owner filters and owner fields do not find those records. The first command only reports:

  ```bash
  python -m app.cli owners backfill
  python -m app.cli owners backfill --commit
  ```

- [ ] Deploy Hub 1.8.0.
- [ ] Verify: sign in through the Hub, create an API key on its Security page, and use it from nano-crucible.

### 3. After the cut-over

- [ ] In a single change, set `CRUCIBLE_AUTH_CLIENTS` (the Hub, nano-crucible, Crucible Lens) and remove every `HUB_AUTH_*` setting. Fields: [the client list](../sign_in_operations.md#the-client-list). The Hub's secret becomes `OAUTH_HUB_CLIENT_SECRET`.
- [ ] Remove the settings that `settings check` reports as retired: `API_CONF_FILE`, `ORCID_CLIENT_ID`, `ORCID_CLIENT_SECRET`, the `HUB_AUTH_ORCID_*` names, `LEGACY_UPLOAD_TOKEN_DOWNSCOPE`.
- [ ] Remove the permission that allowed the server's identity to create storage tokens for clients; the server no longer issues them.
- [ ] Review which projects participate in proposal sync. Every existing project keeps `proposal_sync` enabled; disable it with `PATCH /projects/{project_ref}` for any project that is not the Foundry's record of a proposal.
- [ ] At ORCID, remove the `<API>/auth` redirect.
- [ ] At ORCID, add `<API>/oauth/callback/orcid`, then set `"legacy_callback": false`.
- [ ] Point the cleanup CronJob at `/app/.venv/bin/python -m app.cli auth cleanup`.

### Notes

- **Address settings first.** A 4.0.0 image without `API_PUBLIC_URL` and `API_PATH` serves at the root path. 3.3.1 already reads both, so setting them early has no effect on it.
- **Provider list first.** 4.0.0 refuses to start without it and no longer reads the `HUB_AUTH_ORCID_*` settings. 3.3.1 ignores the new names.
- **Client list last.** 3.3.1 requires `HUB_AUTH_*`, and 4.0.0 refuses to start when both those settings and `CRUCIBLE_AUTH_CLIENTS` are set. The switch may also be made in the same rollout as the image. Until it is made, nano-crucible 4.0 and Lens work with API keys but cannot authenticate users through a browser.
- **Migrations** add tables, columns and triggers and drop nothing, so 3.3.1 continues to run on the migrated database during the rollout. They are listed at the end of this page. One gives every account without a username a generated one and then requires a username, so 3.3.1 cannot create accounts during the rollout. One also moves the grants on instrument records into instrument membership: 3.3.1 keeps authorizing correctly, but its "owned" and "maintained" instrument filters return nothing until 4.0.0 is deployed, and grants written by 3.3.1 in that window are reported, and converted with `--commit`, by `instruments check`.
- **Before the identity lookup is enabled**, ORCID sign-in matches users by the previous method and no user can link a second login.
- **API keys** from before 4.0 are copied into the hashed table by migration `b0e044b67c87`, which then drops the old plain-text table. 3.3.1 reads only that table, so after this migration a rollback to 3.3.1 has no API keys; restore the backup instead. 3.3.1 pods cannot create keys between the migration and the new image.
- **The image** runs as uid 10001 with its code in `/app`. `/root/.venv` and `/root/scripts` remain as symbolic links, so the existing cleanup CronJob command continues to work until it is changed.
- **Hub 1.8.0** refuses to start if one of its secrets is provided in more than one way.

## Docker Compose

The bundle has since moved to [crucible-selfhost](https://github.com/MolecularFoundryCrucible/crucible-selfhost), under `compose/`. Before running `docker compose up`:

- [ ] Back up the database, as described in the [installation guide](https://github.com/MolecularFoundryCrucible/crucible-selfhost/blob/main/compose/docs/operations.md#upgrading).
- [ ] Create the new secret: `openssl rand -hex 32 > secrets/CRUCIBLE_AUTH_PEPPER && chmod 644 secrets/CRUCIBLE_AUTH_PEPPER`.
- [ ] If other hosts access the server, set `CRUCIBLE_BIND_ADDRESS=0.0.0.0` and configure HTTPS. Plain HTTP now works only on `localhost`.
- [ ] If ORCID is used, add `compose.orcid.yaml` to `COMPOSE_FILE`, and either register `https://<your address>/api/v3/oauth/callback/orcid` at ORCID or set `ORCID_LEGACY_CALLBACK=true`.
- [ ] Verify that Docker Engine is version 28 or newer.
- [ ] If the installation predates file storage, create the storage secrets and enable the bundled store: `openssl rand -hex 16 > secrets/S3_ACCESS_KEY_ID`, `openssl rand -hex 32 > secrets/S3_SECRET_ACCESS_KEY`, `chmod 644 secrets/*`, and add `COMPOSE_PROFILES=bundled-storage` to `.env`.
- [ ] Verify that `secrets/CRUCIBLE_SECRET_KEY` has at least 32 characters (`wc -c`); a key generated with the installation guide's command has 64.

After the services are running:

- [ ] If users have previously signed in with ORCID, record their logins. Until then, ORCID sign-in rejects them. The first command only reports; the second writes:

  ```bash
  docker compose run --rm api python -m app.cli identity backfill --issuer https://orcid.org
  docker compose run --rm api python -m app.cli identity backfill --issuer https://orcid.org --commit
  ```

- [ ] Fill the owners of datasets and samples written by 3.x: `docker compose run --rm api python -m app.cli owners backfill`, then again with `--commit`.
- [ ] Verify the instrument grants: `docker compose run --rm api python -m app.cli instruments check` prints only zeros; if not, run it again with `--commit`.
- [ ] Upgrade the Hub to 1.8.0.

Password authentication is now enabled by default; set `CRUCIBLE_AUTH_PASSWORD_ENABLED=false` to allow sign-in through the configured identity provider only.

## Client authors

### Removed routes

In 4.0.0 and 4.0.1 each route answered `410` with `{"detail": {"code": "route_removed", "message": ...}}` naming the replacement; later releases answer `404`.

| Removed | Replacement |
|---|---|
| `GET /account/apikey`, `POST /account/apikey/regenerate` | `POST`, `GET`, `PATCH`, `DELETE /account/apikeys` |
| `POST /users/{user_ref}/apikey`, `POST /users/{user_ref}/apikey/regenerate` | Users create their own keys; administrators use `GET` and `DELETE /users/{user_ref}/apikeys` |
| `GET /auth/login`, `/auth/callback`, `/auth/apikey`, `POST /auth/apikey/regenerate`, `GET /login`, `/auth`, `/user_apikey` | Sign in through `/oauth/authorize`, then `POST /account/apikeys` |
| `POST /datasets/{dataset_mfid}/files/{file_id}/ingest` | `POST /files/{file_id}/ingest` |
| `GET /datasets/{dataset_mfid}/samples` | `GET /samples?dataset_mfid=` |
| `GET /users/by-username/{username}` | `GET /users/{user_ref}`, which accepts a username |
| `GET /users/{user_ref}/datasets`, `GET /users/{user_ref}/samples` | `GET /datasets?accessible_to_user=`, `GET /samples?accessible_to_user=` |
| `POST /datasets/{dataset_mfid}/upload/initiate`, `/upload/initiate/multipart`, `/upload/complete` | The signed multipart routes under `/datasets/{dataset_mfid}/upload/multipart` |

### Changed responses

- `POST /datasets/{parent}/children/{child}` and `POST /samples/{parent}/children/{child}` return `parent_*_mfid`, `child_*_mfid` and `relationship_type`; the internal integer ids are removed.
- The keyword routes return `keyword` and `num_datasets`; the integer `id` is removed.
- `PATCH /ingestion_requests/{id}` changes only `status`, `time_completed` and `ingestion_githash`, and ignores other fields. `ingestion_class` on the ingest routes must be 1 to 128 letters, digits, dots, hyphens or underscores.
- `PATCH /datasets/{id}` and `PATCH /samples/{id}` reject `public` with 422; use `PUT` or `DELETE /resources/{mfid}/access/public`.
- Request bodies over 10 MiB (20 MiB for thumbnails) return 413 `body_too_large`.
- Five OpenAPI schema names changed: `DatasetLinkRead`, `SampleLinkRead`, `KeywordRead`, `ResourceAccessGroupRead` and `IngestionRequestRead`.
- `GET /keywords` and `GET /keywords/{keyword}` require authentication.
- `POST /projects`: only an administrator may name another user as the lead (403 `lead_must_be_caller`), and a service account cannot be a lead (422). Projects carry `proposal_sync`, which only an administrator can set. Where the deployment reserves a naming scheme (`RESERVED_PROJECT_ID_PATTERN`), creating or renaming a project with a reserved `project_id` returns 403 `project_id_reserved` for anyone but an administrator.
- `PATCH /service_accounts/{service_account_ref}` with `platform_role: admin` requires a browser session with a recent sign-in: an API key receives 403 `hub_session_required`, an older session 401 `insufficient_user_authentication`.
- `POST /users/resolve` and `POST /datasets/first_thumbnails` accept at most 1000 entries per list.
- Starting an upload on a server with uploads disabled returns 501 `{"detail": {"code": "feature_disabled", "feature": "uploads", ...}}`; it previously returned 503 with `Retry-After`.
- Instruments are managed through membership. `PUT` and `DELETE /resources/{mfid}/access/users|projects/...` on an instrument return 409 `use_instrument_members`; use `GET`, `POST`, `PATCH`, `DELETE /instruments/{instrument_ref}/users/{user_ref}` with `role` `viewer`, `editor` or `admin`. Projects can no longer hold a role on an instrument. `members`, `role`, `capabilities` and `affiliation=owner|maintainer` keep their shapes and meanings; `affiliation=member` lists every instrument the caller is a member of.
- Every instrument member reads the instrument's datasets, at `viewer`. `affiliation=instrument` on dataset lists, facets and search matches those datasets; `affiliation=member` does not include them. Their grant lists show an `instrument_members` entry.
- `POST /resources/{mfid}/transfer_ownership` on an instrument keeps the previous owner as an `admin` member, and refuses a service account as the new owner (422).
- `instrument_name` is no longer accepted as an input: `POST /datasets` and `PATCH /datasets/{id}` return 422 for a name (a `null` is ignored), and `GET /datasets?instrument_name=` returns 422. Use `instrument_id` or `instrument_mfid`. Responses still carry `instrument_name` as the instrument's display name.
- Records have one shape. Every dataset, sample, instrument and project returns `owner` as a `UserPublicRead`, by default on lists and search too (`include_owner` defaults to true); projects also return `resource_type`, and `GET /projects/search` returns the `GET /projects` model. Datasets and samples return `role`, the caller's effective role.
- Deprecated in responses, still returned: `owner_orcid`; `project_id`, `instrument_id` and `instrument_name` on datasets and samples (use the nested `project` and `instrument`); `lead` and `project_lead_orcid` on projects (use `owner`).
- `GET /datasets/{id}/parents|children` and `GET /samples/{id}/parents|children` return full `DatasetResponse`/`SampleResponse` items with `links` null. Sample detail no longer embeds `datasets` unless `include_datasets=true`.
- `deletion_request` on records is typed (`ActiveDeletionRequestRead`) and no longer carries `requester_user_id` or `reviewer_user_id`. Instrument `members` use the project member shape, `AccessGroupMemberRead`.
- `capabilities.can_delete` means `DELETE /resources/{mfid}?force=true` would be accepted: it is now true for dataset and sample owners and false for project and instrument admins who are not the owner. Instrument `max_grant_role` never says `contributor`.
- Requests name a user with `owner_ref`: in create bodies (replacing `owner`, `owner_orcid` and the `project_lead*` fields), as `new_owner_ref` in ownership transfer (replacing `new_owner`), and as the owner filter, now repeatable with OR (replacing `owner_id`); `owner_id_is_null` becomes `owner_is_null`. The old names remain as deprecated aliases.
- New: `GET /features` returns whether each optional feature (`uploads`, `ingestion`, `printing`, `proposal_sync`, `passwords`) is enabled. The names match the `feature` field of the 501 `feature_disabled` response.

### User authentication

Client applications authenticate users through the standard routes: `/oauth/authorize` with PKCE, then `/oauth/token`, with rotating refresh tokens. A client without a secret registers as a public client and may use the device authorization flow. [Authentication](../sign_in.md) describes the steps, the token response and the errors.

Creating keys, ending sessions and changing logins require a browser sign-in no more than ten minutes old. An API key receives 403 `hub_session_required`.

### Deprecated, still served in 4.0.0

Released clients still use these. They will be removed when the ingestion pipeline and user installations run nano-crucible 4.x. The deployed OpenAPI document marks each one as deprecated.

- `/auth/hub/login`, `/token`, `/refresh`, `/revoke`: use `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`. These will be removed when Hub 1.8.0 is deployed everywhere.
- `POST /users/resolve`.
- Removed after 4.0.1 (now 404): `GET /account/join_requests` (use `GET /join_requests?scope=submitted`), `POST /access_groups/{group_name}/join` (use `POST /projects/{project_ref}/join_requests`), `GET /users/{user_ref}/apikey/verify` (use `api_key_status` on `GET /users/{user_ref}`), the four postprocessing aliases under `/datasets/{dataset_mfid}/` (use `POST /datasets/{dataset_mfid}/postprocess`), `GET` and `POST /resources/{mfid}/access_groups` (use `/resources/{mfid}/access`), and `POST` and `DELETE /users/{user_ref}/access_groups/{group_name}` (use the project, instrument and service-account member routes).
- Removed after 4.0.1: the custom access group routes `POST /access_groups`, `GET /access_groups/{group_name}` and `GET /access_groups/{group_name}/users`; use the project and instrument member routes.
- Request field `owner_orcid`; response fields `resource_id`, `dataset_id`, `sample_id` and `group_name` where an `_mfid` or project field replaced them.

## Developers of this repository

- A local environment file requires `API_PUBLIC_URL` and `API_PATH` in place of `API_CONF_FILE`; see `.env.example-localdev`.
- Database tables are in `app/tables.py`; `app/models/` holds only request and response models, and routes never return a table.
- Authentication code is in `app/auth/`; its browser pages are in `app/api/routes/browser_sign_in.py`.
