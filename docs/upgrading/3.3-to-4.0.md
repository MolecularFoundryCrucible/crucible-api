# Upgrading from 3.3.1 to 4.0.0

4.0.0 keeps every address under `/api/v3`. It is a major release because the API now signs people in itself (several providers, passwords, sessions, an OAuth server for clients), because old ways of getting an API key are gone, and because the image and its settings changed for operators.

Read the part for your role:

- [Kubernetes deployments (the Foundry)](#kubernetes-deployments-the-foundry)
- [Docker Compose installations](#docker-compose-installations)
- [Client authors](#client-authors)
- [Developers of this repository](#developers-of-this-repository)

## What changes

- **Sign-in belongs to the API.** `CRUCIBLE_AUTH_PROVIDERS` lists the providers (ORCID, or any OpenID Connect service), `CRUCIBLE_AUTH_CLIENTS` lists the programs allowed to sign people in, and passwords are an option for small installations. Clients use the standard routes `/oauth/authorize`, `/oauth/token` and `/oauth/revoke`.
- **API keys are created, never read back.** People create named keys with `POST /account/apikeys`; the routes and browser pages that showed or regenerated "the" key answer 410.
- **Settings come from the environment only.** The YAML files in the image and `API_CONF_FILE` are gone.
- **The image runs unprivileged.** uid 10001, code in `/app`, nothing writable except `/tmp` and `/dev/shm`.
- **19 database migrations**, all additive, ending at revision `208288a60073`.

## Release order

API 4.0.0, Hub 1.8.0 and nano-crucible 4.0 ship together: the API first, then the clients, in one window.

| Combination | What breaks |
| --- | --- |
| Hub 1.7.x on API 4.0.0 | "Regenerate key" and the administrators' provision and rotate buttons answer 410. Sign-in keeps working through the deprecated `/auth/hub/*` routes. |
| Hub 1.8.0 on API 3.3.1 | Does not work: it needs the new routes. |
| nano-crucible 3.3.0 on API 4.0.0 | `account api-key` answers 410, and the link `config init` prints (`/user_apikey`) is gone. Everything else works. |
| Crucible Lens before its new sign-in on API 4.0.0 | Cannot sign in: its ORCID screen used `/auth/apikey`. |

## Kubernetes deployments (the Foundry)

### Before deploying the 4.0.0 image

These are safe to do on 3.3.1 and must be in place first.

1. **Address.** Set `API_PUBLIC_URL` (for example `https://crucible.lbl.gov`) and `API_PATH` (`api/v3`, or `testapi-staging`) on the API Deployment. Without them a 4.0.0 image serves at the root path and cannot build its own address. The cleanup CronJob needs neither.
2. **Providers.** Set `CRUCIBLE_AUTH_PROVIDERS` to a list with the ORCID entry, and its secret as `OIDC_ORCID_CLIENT_SECRET`. These replace `HUB_AUTH_ORCID_CLIENT_ID`, `HUB_AUTH_ORCID_ISSUER` and `HUB_AUTH_ORCID_CLIENT_SECRET`. Keep `"legacy_callback": true` in the ORCID entry, so the API keeps using the redirect already registered at ORCID (`<API>/auth/hub/callback`). The fields are in [the provider list](../hub_auth_operations.md#the-provider-list).
3. **Clients.** Either list the Hub and nano-crucible in `CRUCIBLE_AUTH_CLIENTS` (the Hub's secret is then `OAUTH_HUB_CLIENT_SECRET`), or keep `HUB_AUTH_*`, which registers the Hub alone. Setting both stops the server at startup. `HUB_AUTH_CLIENT_SECRET` must be at least 32 characters.
4. **Passwords stay off.** Leave `CRUCIBLE_AUTH_PASSWORD_ENABLED`, `CRUCIBLE_AUTH_PASSWORD_REGISTRATION` and `CRUCIBLE_AUTH_PEPPER` unset to stay ORCID-only.
5. **Security context.** The container runs as uid 10001 and cannot write to its code or to `/root`. It needs a writable `/tmp` and `/dev/shm`. `runAsNonRoot` and a read-only root filesystem with an `emptyDir` on `/tmp` both work.
6. **Pipeline check.** Run `python -m app.cli settings check` without a `-w /root` flag: the image's own working directory is `/app` in 4.0.0 and `/root` in 3.3.1, so one invocation serves both.
7. **Front door.** Apply the sign-in limits written for `/api/v3/auth/hub/*` (small bodies, a bounded wait, rate limits) to `/api/v3/oauth/*` as well, and keep the body limits at 10 MiB, 20 MiB for thumbnails.

The cleanup CronJob command (`/root/.venv/bin/python /root/scripts/cleanup_hub_auth.py`) keeps working: `/root/.venv` and `/root/scripts` remain as links to `/app`.

### The cut-over

1. Back up the database.
2. Apply the migrations: `python -m app.cli db upgrade`. They commit one by one and wait at most `ALEMBIC_LOCK_TIMEOUT` (5 s) for a table lock; rerun the command if one times out. The database ends at `208288a60073`.
3. Deploy the API 4.0.0 image. `GET /health/ready` reports the version, the commit and `schema_state: current`.
4. Record how each person signs in, then turn the lookup on. From inside the pod:

   ```bash
   python migrations/data/20261103_backfill_user_identity.py --issuer https://orcid.org            # dry run
   python migrations/data/20261103_backfill_user_identity.py --issuer https://orcid.org --commit
   ```

   Then set `CRUCIBLE_AUTH_IDENTITY_LOOKUP=true`. Until it is on, ORCID sign-in still finds people by their identifier and linking another sign-in method is unavailable.
5. Copy existing API keys into the hashed table, once:

   ```bash
   python migrations/data/20261106_backfill_api_keys.py            # dry run
   python migrations/data/20261106_backfill_api_keys.py --commit
   ```

6. Deploy Hub 1.8.0. It refuses to start if one of its secrets is given more than one way (file, mounted secret, plain variable).
7. Check: sign in through the Hub, create an API key on its Security page, use the key from nano-crucible 4.0, and run `python -m app.cli settings check` against the rendered manifests.

### After the cut-over

- Remove the settings 4.0.0 no longer reads; `settings check` lists each as retired: `API_CONF_FILE`, `ORCID_CLIENT_ID`, `ORCID_CLIENT_SECRET` and its `_VERSION`, and the `HUB_AUTH_ORCID_*` names.
- Remove the `<API>/auth` redirect from the ORCID application: the browser page that used it is gone.
- When convenient, add `<API>/oauth/callback/orcid` to the ORCID application, then set `"legacy_callback": false`. The old callback address is deprecated.
- Point the cleanup CronJob at `/app/.venv/bin/python /app/scripts/cleanup_hub_auth.py`, so a later release can drop the `/root` links.
- Once Hub 1.7.x is gone, the `/auth/hub/*` routes and the front door rules for them can go in a later release.

## Docker Compose installations

Follow [Upgrading in the install guide](../../deploy/compose/README.md#upgrading). In short, before `docker compose up`:

1. Create the new secret `secrets/CRUCIBLE_AUTH_PEPPER`; passwords are on by default.
2. The server now listens on this machine only. Set `CRUCIBLE_BIND_ADDRESS=0.0.0.0` if other machines use it, and give it HTTPS: plain HTTP is refused under any name but `localhost`.
3. ORCID sign-in moved to its own file. Add `compose.orcid.yaml` to `COMPOSE_FILE`, and either register `https://<your address>/api/v3/oauth/callback/orcid` at ORCID or set `ORCID_LEGACY_CALLBACK=true` to keep the address you registered before.
4. Docker Engine 28 or newer is required.

The `migrate` service applies the database changes before the new API starts. Upgrade the Hub to 1.8.0 in the same window.

## Client authors

### Routes that answer 410

Each answers `410` with `{"detail": {"code": "route_removed", "message": ...}}`, and the message names the replacement.

| Removed | Use instead |
| --- | --- |
| `GET /account/apikey`, `POST /account/apikey/regenerate` | `POST`, `GET`, `PATCH`, `DELETE /account/apikeys` |
| `POST /users/{user_ref}/apikey`, `POST /users/{user_ref}/apikey/regenerate` | People create their own keys; administrators use `GET` and `DELETE /users/{user_ref}/apikeys` |
| `GET /auth/login`, `/auth/callback`, `/auth/apikey`, `POST /auth/apikey/regenerate`, `GET /login`, `/auth`, `/user_apikey` | Sign in through `/oauth/authorize`, then `POST /account/apikeys` |
| `POST /datasets/{dataset_mfid}/files/{file_id}/ingest` | `POST /files/{file_id}/ingest` |
| `GET /datasets/{dataset_mfid}/samples` | `GET /samples?dataset_mfid=` |
| `GET /users/by-username/{username}` | `GET /users/{user_ref}`, which takes a username |
| `GET /users/{user_ref}/datasets`, `GET /users/{user_ref}/samples` | `GET /datasets?accessible_to_user=`, `GET /samples?accessible_to_user=` |

### Responses that changed

- `POST /datasets/{parent}/children/{child}` and `POST /samples/{parent}/children/{child}` return `parent_*_mfid`, `child_*_mfid` and `relationship_type`; the internal integer ids are gone.
- The keyword routes return `keyword` and `num_datasets`; the integer `id` is gone.
- `PATCH /ingestion_requests/{id}` changes only `status`, `time_completed` and `ingestion_githash`, and ignores other fields. `ingestion_class` on the ingest routes must be 1 to 128 letters, digits, dots, hyphens or underscores.
- `PATCH /datasets/{id}` and `PATCH /samples/{id}` refuse `public` with 422; use `PUT` or `DELETE /resources/{mfid}/access/public`.
- Request bodies over 10 MiB (20 MiB for thumbnails) answer 413 `body_too_large`.
- Five OpenAPI schema names changed: `DatasetLinkRead`, `SampleLinkRead`, `KeywordRead`, `ResourceAccessGroupRead` and `IngestionRequestRead`.

### Signing people in

A program signs people in as a registered client: `GET /oauth/authorize` with PKCE, then `POST /oauth/token`, with refresh tokens that rotate. Programs without a secret (a command line, a desktop or mobile app) register as public clients and use a loopback redirect or the device flow (`POST /oauth/device_authorization`). `GET /.well-known/oauth-authorization-server` lists the endpoints, and `GET /auth/methods` the ways to sign in. The token answer carries `expires_in`, `refresh_expires_in`, `user_unique_id` and, when known, `auth_time`.

Some actions need a person at a browser with a sign-in in the last ten minutes: creating keys, ending sessions, changing how someone signs in, changing administrators. An API key gets 403 `hub_session_required`, a session approved with a device code gets 403 `browser_sign_in_required`, and an older session gets 401 `insufficient_user_authentication`.

### Deprecated, still served in 4.0.0

These keep working because released clients use them. They go once the ingestion pipeline and people's installations are on nano-crucible 4.x, at the later move to `/api/v4`, unless a date is announced earlier.

- `/auth/hub/login`, `/auth/hub/token`, `/auth/hub/refresh`, `/auth/hub/revoke`: use `/oauth/authorize`, `/oauth/token` and `/oauth/revoke`. They go once Hub 1.8.0 is deployed everywhere.
- `POST /users/resolve`, `GET /account/join_requests`, `POST /access_groups/{group_name}/join`, `GET /users/{user_ref}/apikey/verify`.
- The legacy upload routes under `/datasets/{dataset_mfid}/upload/`: use the signed multipart routes.
- The four postprocessing aliases under `/datasets/{dataset_mfid}/`, and the `/resources/{mfid}/access_groups` and `/users/{user_ref}/access_groups/{group_name}` routes.
- The request fields `owner_orcid` and `instrument_name`, and the response fields `resource_id`, `dataset_id`, `sample_id` and `group_name` where an `_mfid` or project field replaced them.

The deployed OpenAPI document marks every deprecated route, parameter and field.

## Developers of this repository

- A local environment file needs `API_PUBLIC_URL` and `API_PATH` in place of `API_CONF_FILE`; see `.env.example-localdev`.
- Database tables are in `app/tables.py`; `app/models/` holds only request and response models, and routes never return a table.
- Sign-in code is in `app/auth/`; its browser pages are in `app/api/routes/browser_sign_in.py`.
