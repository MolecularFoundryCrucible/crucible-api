# Uploads

This page specifies the signed multipart upload routes and the storage configuration behind them. File content never passes through the API: clients send parts directly to the object store through signed URLs, and the API performs every storage operation inside the request, with no background worker.

## Routes

All routes accept an API key or an access token in `Authorization: Bearer <credential>` (see [Authentication](sign_in.md)). An upload session belongs to the user who started it: status, part signing and completion require that user and CREATE on the dataset, evaluated in the request's privilege mode. The owner can abort a session after losing access to the dataset. Every response under `/upload/multipart/` has `Cache-Control: no-store`.

| Method and path | Request | Success |
| --- | --- | --- |
| `POST /datasets/{dataset_mfid}/upload/multipart/initiate` | `filename`, integer `size` (0 for an empty file), optional lowercase `sha256_hash`; optional `Idempotency-Key` header (1 to 128 characters) | 200 with state `uploading`, or state `completed` with `existing_file` (see [Deduplication](#deduplication)) |
| `POST /files/{file_mfid}/upload/multipart/initiate` | `size`, optional `sha256_hash`; optional `Idempotency-Key` and `If-Match` headers | Starts a replacement of the file's content; see [File replacement](file_replacement.md) |
| `POST /datasets/{dataset_mfid}/upload/multipart/{upload_id}/parts` | `parts`: 1 to 64 objects with `part_number` and `crc32c` | 200 signed PUT URLs with the headers to send, offsets, sizes and expiry |
| `GET /datasets/{dataset_mfid}/upload/multipart/{upload_id}` | Optional `part_number_marker` (0 to 10000) and `limit` (1 to 1000) | 200 session state; while `uploading`, the parts the store has received and `next_part_number_marker` |
| `POST /datasets/{dataset_mfid}/upload/multipart/complete` | `upload_id`, lowercase `sha256_hash`, canonical base64 `crc32c` | 200 `AssociatedFileRead` |
| `DELETE /datasets/{dataset_mfid}/upload/multipart/{upload_id}` | No body | 204 after cleanup; repeatable |

```json
{
  "upload_id": "server-generated-opaque-id",
  "upload_protocol": "xml-multipart-signed-v1",
  "state": "uploading",
  "expires_at": "2026-10-19T12:00:00Z",
  "part_size": 16777216,
  "part_count": 8,
  "parts": [],
  "next_part_number_marker": null,
  "existing_file": null,
  "failure_code": null
}
```

Session states are `uploading`, `completed`, `aborted`, `failed` and `expired`. `initiating` and `finalizing` are transient states held while an initiate or complete request is in progress; a client that sees `finalizing` after a lost response retries completion.

The routes `POST /datasets/{dataset_mfid}/upload/initiate`, `/upload/initiate/multipart` and `/upload/complete` were removed in 4.0.0; the server no longer issues storage tokens.

## Sessions and filenames

- The object key is `{dataset_mfid}/_files/{upload_id}`, generated by the server and never overwritten. The filename exists only in the database. See [Storage locations and downloads](storage_downloads.md) for the layouts of stored objects.
- A filename is 1 to 1024 characters, a relative path without empty or dot segments, backslashes or control characters.
- A filename that already exists in the dataset, or is reserved by another active session, is refused with 409.
- An idempotency key is scoped to the owner, the dataset and the protocol; reusing it with different request fields returns 409. Keep the same key across initiation retries: a retry after a lost response reuses the session and its provider upload.
- A session expires seven days after initiation. An initiation that never completes its storage call releases its reservation after ten minutes.
- Initiation reserves the file's size against the owner's and the dataset's quotas (see [Settings](#settings)).

## Parts

The API chooses the part size per session and returns it as `part_size`: the file size divided by 8, rounded up to a whole MiB, between 8 MiB and 64 MiB. Every part is exactly `part_size` bytes except the last. Plan parts from the returned `part_size`, not from a client-side constant. The maximum file size is 500 GiB.

An empty file (`size` 0) has `part_size` 0 and `part_count` 0: request no part URLs and complete directly with the SHA-256 and CRC32C of empty content (`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` and `AAAAAA==`). The API checks both and writes the empty object itself.

Compute the canonical base64 CRC32C of each part before requesting its URL; once authorized, a part's checksum cannot change. A URL signs PUT, the exact object, upload ID, part number, checksum header and content length. URLs expire after at most 15 minutes and never after the session; request expired URLs again with the same checksums. Part signing is limited to one request per session per signing interval (five seconds by default). Request about 32 URLs per call and upload about 8 parts concurrently so the interval does not limit throughput.

Send every header returned for a part except `Content-Length`, and do not hard-code provider header names. In browsers, pass the exact Blob slice as the body and let the browser set `Content-Length`. Signed URLs are bearer capabilities: keep them out of logs, analytics, persistent resume files and error reports.

To resume, follow every `next_part_number_marker`, skip the part numbers already received, and request URLs for the missing parts. A provider ETag is an opaque completion identifier, not a SHA-256 digest.

## Completion

Completion lists every part, compares part numbers and sizes with the session geometry and the authorized checksums, assembles the object, verifies its size and CRC32C, publishes the file record, and aborts any leftover provider uploads for the object. Large uploads can take several seconds to complete; use a request timeout of about two minutes. Completion is safe to retry: an assembled object is verified and published, and a published file is returned. Missing or mismatched parts and checksums fail the session, abort its provider uploads and delete the unpublished object; start a new session after correcting the source.

CRC32C is enforced per part by the store and for the whole object by the API. The SHA-256 is the client's claim: completion records it with `sha256_verified_at` null, and the API never computes it.

Signed URLs already issued remain usable until they expire or the provider upload is aborted. A completed session keeps its file identifier for retries; if that file has since been deleted, completion returns 410.

### Deduplication

Initiation returns state `completed` with `existing_file`, and creates no session, when the dataset already holds a file with the same filename, `sha256_hash` and `size` whose `sha256_verified_at` is set. No route of this API sets `sha256_verified_at`.

## Errors

| Condition | Response |
| --- | --- |
| `MULTIPART_UPLOAD_ENABLED` is not `true` (both initiate routes) | 501 `{"detail": {"code": "feature_disabled", "feature": "uploads", "message": ...}}`; sessions already started can still finish. `GET /features` reports `uploads: false` |
| File larger than `MAX_UPLOAD_BYTES` | 413 |
| Owner or dataset quota exceeded | 429 with `Retry-After: 60` |
| Filename exists in the dataset | 409 `{"detail": {"code": "filename_exists", "file_mfid": ..., "etag": ..., "message": ...}}` |
| Filename reserved by another session; idempotency key reused with other fields | 409 with a string `detail` |
| Dataset pending deletion | 409 `pending_deletion` |
| Part signing within the signing interval | 429 with `Retry-After` |
| Part number beyond the session's part count | 422 |
| Changed checksum for an authorized part, or changed claim at completion | 409 |
| Session expired (part signing, completion) | 410 |
| Session aborted or failed; completion before every part is authorized | 409 |
| Provider upload no longer exists (status) | 409; abort and start a new session |
| Verification failed | 422 `Upload failed verification: <code>`; the session fails |
| Publication refused (filename taken, dataset deleted or pending deletion) | 409 `Upload could not be published: <code>` |
| Abort of a completed session | 409; delete the file through `DELETE /files/{file_id}` |
| Storage unavailable | 503; initiation, completion and abort include `Retry-After: 5` |

## Reference client

`python -m scripts.multipart_upload_client --api https://host/api-root --dataset DATASET_MFID --file data.h5 --state upload-resume.json`

The credential is read from `CRUCIBLE_API_TOKEN` (`--token-env` names another variable). The resume record contains a source fingerprint, the idempotency key and the upload ID, with no credentials or signed URLs; use one client process per resume record. The client computes the SHA-256, the whole-object CRC32C and each part's CRC32C, signs 32 parts per call, uploads 8 parts in parallel and completes once. Running it again resumes the same session and skips the parts already received. Keep the source file unchanged. nano-crucible 3.3.0 and later use this protocol.

## Settings

| Variable | Default and purpose |
| --- | --- |
| `STORAGE_STORES` | Required when files are stored: the stores, a JSON list ([Stores](#stores)); usually given as a file with `STORAGE_STORES_FILE` |
| `STORAGE_DEFAULT_STORE` | The id of the store uploads use when nothing chooses another; required when `STORAGE_STORES` lists more than one |
| `STORAGE_{ID}_ACCESS_KEY_ID`, `STORAGE_{ID}_SECRET_ACCESS_KEY` | Required for each `s3` store, as secrets |
| `STORAGE_{ID}_CREDENTIALS` | Optional for a `gcs` store: a service account key file, for a server outside Google Cloud |
| `MULTIPART_UPLOAD_ENABLED` | `false`; controls initiation only |
| `MAX_UPLOAD_BYTES` | 500 GiB, which is also the maximum |
| `MULTIPART_OWNER_SESSIONS` | 8 concurrent sessions per owner |
| `MULTIPART_DATASET_SESSIONS` | 32 concurrent sessions per dataset |
| `MULTIPART_OWNER_BYTES` | 1 TiB reserved per owner |
| `MULTIPART_DATASET_BYTES` | 4 TiB reserved per dataset |
| `MULTIPART_SIGNING_INTERVAL_SECONDS` | 5 seconds per session |
| `STORAGE_CLEANUP_ENABLED` | `false`; enables `storage cleanup` (below) |
| `FILE_VERSION_RETENTION_DAYS` | 14; how long replaced and deleted content is kept before `storage cleanup` removes it (see [File replacement](file_replacement.md)) |


`{ID}` is the store's id in capitals, with `-` written as `_`: the store `mf-storage-prod` reads `STORAGE_MF_STORAGE_PROD_CREDENTIALS`.

The single-store settings of earlier releases (`STORAGE_BACKEND`, `UPLOAD_BUCKET`, `STORAGE_READ_BUCKETS`, `GCS_PROJECT`, `S3_ENDPOINT_URL`, `S3_PUBLIC_URL`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `MULTIPART_UPLOAD_BUCKET`, `MULTIPART_UPLOAD_SIGNER`, `MULTIPART_UPLOAD_PROJECT`) are retired: the server refuses to start while one is set and names its replacement.

## Stores

A store is a bucket the API manages: it signs uploads and downloads, keeps versions and deletes content. `STORAGE_STORES` lists them; [`stores.example.json`](stores.example.json) shows a Google Cloud Storage store and an S3-compatible one. Each entry has:

| Field | Meaning |
| --- | --- |
| `id` | Lowercase letters, digits and single hyphens, starting with a letter, at most 63, for example `mf-storage-prod`. Recorded on every file; never change it once files use it |
| `display_name`, `description` | Shown to clients by `GET /storage/stores` |
| `type` | `gcs` or `s3` |
| `bucket` | The bucket new uploads go to |
| `read_buckets` | Optional: other buckets this store's existing records may point at, served read-only |
| `endpoint_url`, `public_url`, `region` | For `s3`: the address the API reaches the store on (required), the address in signed URLs, which clients must reach (default `endpoint_url`), and the region (default `us-east-1`) |
| `project`, `service_account` | For `gcs`: the storage client's project, and a service account the server acts as for this store, which it needs when its own identity cannot sign URLs (GKE Workload Identity, Workload Identity Federation); the server's identity needs Service Account Token Creator on it |

Every stored file records its store. An upload goes to the store it names (`store_id` in the initiation request), else the default of the dataset's project, else that of its instrument, else `STORAGE_DEFAULT_STORE`. Project and instrument admins set those defaults with `PATCH /projects/{project_ref}/settings` and `PATCH /instruments/{instrument_ref}/settings` (`{"default_store_id": "<id>"}`, a JSON Merge Patch with `ETag` and `If-Match`; members read them with `GET`). A replacement goes to the file's store unless it names another. A request naming a store that is not configured answers 422 `unknown_store`; a project or instrument default naming one is skipped.

When a store is removed from `STORAGE_STORES`, its files keep their store id: their metadata stays readable, their download links and replacements answer 503 `store_unavailable`, the dataset's download links map them to `null`, and `storage cleanup` leaves their content. Deleting such a file still keeps its content for the grace period, and configuring the store again restores them. `python -m app.cli storage stores` lists the stores with their file counts and exits 1 when files are in a store that is not configured or have none.

### Moving from the single-store settings

Files stored by earlier releases have no store recorded and answer 503 `store_unavailable` until they get one:

1. Replace the retired settings with `STORAGE_STORES`, one store for the existing bucket.
2. Run the release's migrations.
3. Run `python -m app.cli files assign-store --store <id>`, then again with `--commit`: it records the store on every stored file, file version and upload session without one.
4. Run `python -m app.cli files backfill-locations --store <id>` (see [Missing storage paths](storage_downloads.md#missing-storage-paths)), then again with `--commit`.

## Google Cloud Storage

A `gcs` store's identity is its key file (`STORAGE_{ID}_CREDENTIALS`) when given, else the server's Application Default Credentials: an attached service account, Workload Identity, or a key file named by `GOOGLE_APPLICATION_CREDENTIALS`. With `service_account` set, the server acts as that account for every operation on the store, and its identity needs Service Account Token Creator on it ([impersonated credentials](https://google-auth.readthedocs.io/en/latest/reference/google.auth.impersonated_credentials.html)). URLs are signed locally with a key file, otherwise through IAM signBlob, for which an attached account needs Token Creator on itself. The account needs object access on the store's bucket (and the record bucket for the default store) and read access on its `read_buckets`.

The upload bucket needs:

- A lifecycle rule that aborts incomplete multipart uploads, with an age beyond the seven-day session lifetime. Where `storage cleanup` is not enabled, it is the only cleanup for sessions abandoned without an abort request.
- A CORS rule for browser clients: their origins, `PUT`, the returned request headers (`content-type`, `x-goog-hash`), and `ETag` exposed.

Google's S3 interface is not supported, because it does not check part or whole-object checksums: an `s3` store refuses an `endpoint_url` on `googleapis.com`.

## S3-compatible stores

Part URLs are presigned with SigV4 and bind the part's CRC32C and length (`x-amz-checksum-crc32c` and `Content-Length`, both returned as headers to send), so the store refuses a part with other content. Many S3 servers do not report a whole-object CRC32C, so the API combines the authorized part checksums and sizes and compares the result with the completion claim. When the store lists each part's own CRC32C (Versity S3 Gateway does; SeaweedFS 4.51 does not), the API first compares those with the authorized values; otherwise the check depends on the store enforcing the signed checksum. A store is supported only if `storage check` passes on it.

Signed URLs embed the store's `public_url`: a client that reaches the store by another address receives signature errors. Objects are recorded with `storage_backend` `"gcs"`, which means "stored by the API" on every backend ([Remote file records](remote_file_records.md)). The Docker Compose bundle and external S3 stores are covered in the [installation guide](https://github.com/MolecularFoundryCrucible/crucible-selfhost/blob/main/compose/docs/storage.md).

## Operations

1. Bring the database to the current revision with `python -m app.cli db upgrade`.
2. Create the upload bucket with the access, lifecycle and CORS rules above.
3. Run `python -m app.cli storage check`, then set `MULTIPART_UPLOAD_ENABLED=true`.

`python -m app.cli storage check` uploads a two-part file under `_crucible-check/` in each store (`--store` names one), checks that the store refuses a part whose bytes do not match the signed checksum, completes the upload, downloads it through a signed URL, and deletes it. `--public` signs for an `s3` store's `public_url`, `--keep` leaves the test file, and `--size-mib` sets the first part's size. CI runs it against SeaweedFS and Versity S3 Gateway.

`python -m app.cli storage cleanup` aborts sessions that expired or whose cleanup failed, and deletes replaced and deleted content past its retention period. Run it hourly; it does nothing unless `STORAGE_CLEANUP_ENABLED=true` (the bundle sets it), except with `--dry-run`. `--batch` caps the sessions and versions handled per run (default 500).

Failed verification and abort requests clean up immediately; when storage is unavailable during that cleanup, `storage cleanup` or the bucket's lifecycle rule removes the remains. Session records are retained: inspect `state`, `failure_code` and `cleaned_at`. On Google Cloud Storage, object holds and retention policies can prevent deletion and require operator intervention.
